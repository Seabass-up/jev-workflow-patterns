# H38: Feature-matrix provenance and holdout challenger

Make semantic-feature revisions and held-out evidence bindings inspectable while deterministic code owns metric comparison.

## State contract

Supply a compact named JSON object with these required fields:

- <code>feature_set_revision</code>
- <code>holdout_summary</code>
- <code>code_metric_comparison</code>
- <code>proposed_change</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>evaluation_binding</code>.

~~~json
{
  "evaluation_binding": {
"type": "choice",
"instructions": "Does the supplied evidence establish a valid held-out evaluation binding for proposed_change? Read whether the record names a pinned proposed revision, baseline, held-out split, metric, and validity status. code_metric_comparison is code's deterministic calculation; do not compare numbers, infer improvement, train a model, deploy features, or inspect training data.",
"criteria": {
  "valid_heldout_binding": "The supplied records explicitly bind the proposed and baseline revisions to the same named held-out split and metric, and no leakage/invalidity is stated.",
  "leakage_or_invalid": "The supplied records explicitly identify target leakage, a non-held-out comparison, a changed/unstated split, or another invalid evaluation condition.",
  "incomplete_binding": "The supplied records do not establish the required revision, split, metric, baseline, or validity binding."
}
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code stores question/data revisions, computes metric deltas, protects held-out splits, and requires a model owner to approve any release.

**Code and governance own:** Dataset splits, metric calculation, training, feature storage, deployment, and downstream decisions.

**Simpler baseline:** Adopt feature questions based on intuition or training-set fit alone.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H20's confidence/adjudication record and L06's memory-update category, this binds semantic feature questions to row-level provenance and a held-out challenger while code performs the numeric comparison.

## Limits and source

A valid held-out binding or code-calculated improvement can still be noisy or non-generalizable and says nothing about fairness or causal validity.

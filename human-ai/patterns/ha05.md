# HA05 — Two speakers use the same term in different senses

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Detect an explicitly evidenced meaning mismatch around one term in a learning conversation.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Allows the assistant to clarify vocabulary before arguing about a conclusion the speakers do not share.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `target_term`
- `first_speaker_use`
- `second_speaker_use`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA05-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "target_term": "valid",
  "first_speaker_use": "By valid I mean that every required column contains a value. This table is valid because I believe no required cell is blank.",
  "second_speaker_use": "I also use valid to mean that every required column contains a value. This table is not valid: the required code cell in the final row is blank."
}
```

Expected label: `shared_sense`.

The speakers explicitly give the same definition of valid. Their disagreement concerns whether the table meets that definition, not the term's meaning.

## Code-owned responsibilities

Code binds utterances to stable speaker/message IDs and preserves originals. A host asks one neutral clarification, rather than silently rewriting what either person meant.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

At most one clarification asking which supplied meaning was intended; unresolved cases stay unknown.

## Verification recipe

Human adjudicators compare explicit definitions and contextual uses, including same-sense disagreement and insufficient evidence.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [Use Clear Words](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o3p01-clear-words/) (HL-S2). W3C supplemental guidance recommends explaining jargon and uncommon or application-specific meanings. This motivates detecting an explicitly demonstrated vocabulary mismatch, without inferring disability or reading level.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

# SA06 — Discount request is one the policy text describes

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Classify whether the kind of discount a prospect requests, and the situation they state, is described, excluded, or not mentioned by the seller's discount policy text.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Sends requests the policy already covers to the standard path and everything else to a person, while code checks every percentage and threshold.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `discount_request`
- `discount_policy`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `SA06-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "discount_request": "We're happy to prepay the full year up front, so we'd like the annual prepayment discount applied. On top of that, since we came to you as a referral from Hollis Freight, who are already a customer of yours, we're hoping you can add a referral discount on the same order.",
  "discount_policy": "Discounts available: (a) an annual prepayment discount when the full contract value is paid in advance; (b) a volume discount for orders above the published seat threshold; (c) a nonprofit discount with proof of registered status. Not offered: discounts on implementation, training, or professional services. Resellers are not eligible for any discount and purchase at partner pricing. All discounts require approval from the regional sales director."
}
```

Expected label: `not_covered_by_policy`.

The request asks for two kinds of discount: the annual prepayment discount, which the policy describes, and a referral discount, which the policy neither offers nor names as not offered; the contract's order for multiple kinds (excluded, then not_covered, then described) selects not_covered_by_policy.

## Code-owned responsibilities

Code compares the requested percentage, amount, seat count, and term against the policy's limits exactly, records the policy revision, and routes anything but a within-limit described_in_policy request to the approver named in the policy; the model never grants a discount.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a not_covered_by_policy or excluded_by_policy label goes to the approver with the request text unchanged.

## Verification recipe

Compare labels with the approval path each discount request actually followed over a quarter; review every described_in_policy that an approver later treated as an exception.

This describes required verification work, not checks already performed.

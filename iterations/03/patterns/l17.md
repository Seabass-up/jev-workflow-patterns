# L17: Re-check a shortlisted agent skill choice

Give a code-chosen shortlist a detailed choose-or-none re-check before an agent loads a skill.

## State contract

Supply a compact named JSON object with these required fields:

- <code>user_task</code>
- <code>skill_shortlist</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>skill</code>.

~~~json
{
  "skill": {
    "type": "choice",
    "instructions": "Apply these four mutually exclusive tiers in this exact order. (1) Select insufficient if user_task is missing, empty, unreadable or unclear; if skill_shortlist is missing/empty/unreadable; if any offered entry lacks a full usable description; if the needed capability set cannot be determined; or if a task-required capability is not described by any offered entry. Do not choose an apparently fitting entry while any offered description is unavailable, because an undescribed candidate cannot be compared. (2) Select multiple_required only if every relevant entry has a full usable description, no single offered entry can complete the task, and two or more distinct listed entries are each necessary and together cover it. (3) Otherwise, if one or more fully described offered entries can each complete the whole task, select the most direct/best fit; if equally fitting, select the earliest listed. (4) Select no_skill only if the task and every offered description are clear, none of the offered entries materially fits, and no specific required capability is missing from this shortlist. no_skill means no fit in this shortlist, not none in the full catalog. Judge descriptions, not names. A suggestion never loads a skill or authorizes action.",
    "criteria": {
      "document_editor": "One fully described offered document-editing skill, used alone, directly and sufficiently performs the clear requested task; all offered entries have usable descriptions.",
      "data_analysis": "One fully described offered structured-data analysis skill, used alone, directly and sufficiently performs the clear requested task; all offered entries have usable descriptions.",
      "browser_test": "One fully described offered browser-testing skill, used alone, directly and sufficiently performs the clear requested task; all offered entries have usable descriptions.",
      "multiple_required": "All needed entries are fully described; no single offered skill can complete the clear task, but at least two distinct listed skills are each required and together cover it.",
      "no_skill": "The task and every offered description are clear, none of the offered skills materially fits, and no specific required capability is known to be omitted.",
      "insufficient": "Task/list evidence is missing, empty, unreadable, or ambiguous; any offered entry lacks a full usable description; needed capabilities cannot be determined; or a clear required capability is absent from the offered shortlist."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** For one selected entry, inspect that skill before loading it. multiple_required proposes a code-controlled sequence. insufficient proposes review or a broader candidate search. no_skill means no fit in this shortlist and proposes expanding or reviewing candidate search before concluding no available skill fits.

**Code and governance own:** Initial broad roster ranking, candidate inclusion, skill loading, permissions, and task execution.

**Simpler baseline:** Load every superficially matching skill into the prompt.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike L04's one-pass available handler selection, this is the second, detailed choose-or-none stage after code has formed a broad roster shortlist.

## Limits, source, and shared skill

The result is shortlist-bounded: no_skill does not establish that the full catalog lacks a fit. Code owns candidate coverage, exact membership, skill loading, permissions, and execution. Missing or ambiguous task/list inputs route to review.

Version 3 makes every incomplete offered description an explicit insufficient-evidence trigger. In the v2 screen, Jev selected document_editor at 0.99 for a fixture with an unavailable data_analysis description; that miss is preserved. One bounded v3 re-screen covers the same six states and expectations, with no fixture edits.

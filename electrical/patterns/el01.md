# EL01 — Symptom category for electrical dispatch

[Electrical catalog]({{ '/electrical/' | relative_url }}) · [Evaluation and limitations]({{ '/electrical/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/electrical.md)

Classify the electrical symptom a customer describes so dispatch can assign the right visit type.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/electrical/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Sorts service requests by what the customer actually reports instead of by keyword, while dispatch keeps the scheduling decision.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `customer_report`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

If more than one symptom is reported, select the first that applies in this order: burning_smell_or_heat, breaker_trips, no_power_to_area, flicker_or_dimming, new_work_request.     "criteria": {

```json
      "flicker_or_dimming": "Lights flicker, dim, or brighten, possibly when appliances run.",
      "burning_smell_or_heat": "A burning smell, smoke, scorch marks, or a hot device, outlet, or panel is reported.",
      "new_work_request": "The report asks for new installation or an upgrade rather than reporting a fault.",
      "unknown": "Required evidence is missing, contradictory, or does not support a determinate classification."
    }
  }
}
```

## Policy recorded with its option count

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `EL01-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "customer_report": "We'd like a quote to add a dedicated circuit for a hot tub on the back patio. While you're here, the kitchen lights dim whenever the microwave and toaster run at the same time, and twice last week the breaker labeled 'kitchen' tripped when both were on. Nothing smells or feels warm; we reset it and it holds until the next time."
}
```

Expected label: `breaker_trips`.

The report contains three symptoms (a new work request, dimming, and breaker trips), and the contract's stated precedence puts breaker_trips ahead of flicker_or_dimming and new_work_request regardless of which one the customer states first or treats as the main ask.

## Code-owned responsibilities

Code owns scheduling, technician assignment, and the rule that any burning_smell_or_heat report is escalated immediately; it never treats the label as a diagnosis.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; ambiguous reports go to a dispatcher call-back, not another model call.

## Verification recipe

Compare labels with dispatcher categorizations on a month of real requests, then with the technician's finding after the visit.

This describes required verification work, not checks already performed.

## Source inspiration

- [NFPA 70E, Standard for Electrical Safety in the Workplace (NFPA overview page)](https://www.nfpa.org/codes-and-standards/nfpa-70e-standard-development/70e) (ES-1). NFPA describes 70E as requirements for safe work practices that protect personnel by reducing exposure to major electrical hazards, originally developed at OSHA's request, helping avoid injuries and fatalities from shock, electrocution, arc flash, and arc blast, and assisting compliance with OSHA workplace electrical rules. Motivates EL02 as a text classification of reported hazard signs; the standard, not the label, governs practice.
- [NFPA 70, National Electrical Code (NFPA overview page)](https://www.nfpa.org/codes-and-standards/nfpa-70-standard-development/70) (ES-2). NFPA describes NFPA 70, the National Electrical Code, as enforced in all 50 states and the benchmark for safe electrical design, installation, and inspection to protect people and property from electrical hazards, with edition, amendment, and errata records. Motivates EL01, EL03, EL04, EL07; no article is cited and no rule is applied by the model.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

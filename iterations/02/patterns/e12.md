Find operational steps that omit or contradict their declared safety/availability prerequisites.

## State contract

Supply a small, named JSON object. Required fields:

- `runbook_step`
- `preconditions`

The state is evidence, not an instruction channel. Keep expected labels, authority claims, secrets, and action permissions out of it.

## Exact Jev question contract

```json
{
  "decision": {
    "type": "choice",
    "instructions": "How well does `runbook_step` account for the named `preconditions`? Compare explicit conditions and checks, not the technical correctness of the action itself.",
    "criteria": {
      "covers": "The step explicitly checks or requires every named precondition before the action.",
      "partial": "The step addresses some named preconditions but leaves at least one out.",
      "contradicts": "The step explicitly proceeds despite a named precondition saying it must not.",
      "missing": "The step or preconditions are absent, too vague, or cannot be compared."
    }
  }
}
```

## Code-owned decision envelope

**Follow-up proposal:** Add the missing check or ask the runbook owner to resolve the contradiction; execute no operation from this semantic result.

**Code and governance own:** Perform exact health checks, access checks, change control, timers and action execution.

**Baseline this improves on:** Read the action sentence and assume conditions are understood.

## Provisional confidence handling

- Choice/Score confidence floor: `0.8`
- Noul positive floor: `0.8`
- Noul negative ceiling: `0.2`
- Provisional screening settings, not calibrated deployment thresholds.

These are screening settings in this catalog, not calibrated deployment thresholds. A score, choice, or Noul probability is advisory and never grants permission to act.

## Why it is distinct from Iteration 1

Unlike E02's test/requirement coverage, this checks operational action prerequisites.

## Limits and sources

The prompt cannot establish actual environment health.

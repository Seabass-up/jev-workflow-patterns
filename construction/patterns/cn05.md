# CN05 — Safety observation: stop-work condition, hazard to correct, or housekeeping

[Construction catalog]({{ '/construction/' | relative_url }}) · [Evaluation and limitations]({{ '/construction/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/construction.md)

Classify a written safety observation against the project's complete supplied stop-work list, separating list-matched stop-work conditions from unlisted correctable hazards, housekeeping items, and positive observations.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/construction/evaluation/' | relative_url }}) for observed results; the fixture labels below are frozen expectations, not safety determinations.

<div class="callout warning"><p><strong>Provisional.</strong> The v2 screen matched 6/7 synthetic cases. Jev chose <code>positive_no_deficiency</code> for CN05-7, where an empty required stop-work list was expected to produce <code>unknown</code>. The v1 CN05-4 disagreement and the v2 miss are both preserved; no output was tuned or relabeled.</p></div>

## Proposed benefit

Routes listed stop-work conditions to the standing notification and unlisted deficiencies to the human corrective-action workflow. The competent person on site decides whether work actually stops and the project procedure determines response urgency.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `observation_text`
- `stop_work_conditions`

Supply the complete `stop_work_conditions` list from the project's safety plan. A consuming implementation should deterministically return `unknown` without invoking Jev when either required field is absent or empty; the model is not the required-field gate. This pattern collection does not include or verify that consumer. An unlisted active hazard is `hazard_to_correct`, not an indication that it is safe or that work should continue. The competent person and project response procedure retain those decisions.

## Code-owned responsibilities

Consumer code must own the complete stop-work list and its revision, the required-field gate, the observation record, the queues, corrective-action tracker, and standing notification triggered by a list-matched `stop_work_condition`. Route `hazard_to_correct` for human review under project procedures. This collection does not implement or verify those consumer behaviors. No label says that a condition is safe, sets response urgency, or decides whether work stops; the competent person on site decides under applicable project policy.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a list-matched `stop_work_condition` triggers the standing notification. Other hazards remain in the observation/corrective-action workflow for human review.

## Verification recipe

Compare labels with the safety manager's classification of authorized observation cards; measure missed list-matched stop-work conditions first, then verify that unlisted hazards reach human review and that missing list evidence is held as unknown by the deterministic preflight.

This describes required verification work, not checks already performed.

# H40: Semantic-feature drift and retraining hold

Stop a semantic-feature pipeline from silently reusing an old evaluation after question, population, or held-out behavior changes.

**Contract version 2:** An absent/incomplete or regressed held-out receipt is the first hold; otherwise classify multiple changed dimensions before a single changed dimension and call stable only on a complete current binding. The current cases cover all answer labels; see the evaluation record for synthetic results. This is not production qualification.

## State contract

Supply a compact named JSON object with these required fields:

- <code>feature_pipeline_state</code>
- <code>change_evidence</code>
- <code>evaluation_receipt</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>drift_status</code>.

~~~json
{
  "drift_status": {
    "type": "choice",
    "instructions": "Classify current re-evaluation status from feature_pipeline_state, change_evidence, and evaluation_receipt. Apply this order: heldout_regressed_or_missing when the receipt is absent/incomplete or explicitly reports held-out regression; multiple_material_changes when two or more distinct change dimensions (question/model/policy vs population/source) are explicitly shown and no receipt-failure/regression has priority; question_or_policy_changed for a single question/model/policy revision; population_or_source_changed for a single material source/population shift; otherwise stable_under_bound_receipt only when the complete receipt binds the current revisions and population and no material change is recorded. Do not calculate drift metrics, retrain, deploy, or decide a business outcome.",
    "criteria": {
      "stable_under_bound_receipt": "A complete evaluation receipt binds the current question/model/policy revisions and source population, reports no held-out regression, and no material post-receipt change is shown.",
      "question_or_policy_changed": "Exactly one semantic question, criteria, model, or policy revision differs from the bound evaluation; the receipt is otherwise present and complete, and no material population/source change is shown.",
      "population_or_source_changed": "Exactly one material source population, collection, or input-distribution change is shown after a complete bound evaluation; no question/model/policy revision is shown.",
      "multiple_material_changes": "At least two distinct dimensions among question/model/policy revision and source-population/input-distribution change are explicitly shown after a complete prior evaluation; no missing/incomplete receipt or held-out regression is shown.",
      "heldout_regressed_or_missing": "The evaluation receipt is missing/incomplete, cannot establish a completed held-out evaluation, or explicitly reports held-out regression; this hold reason takes precedence over listed changes."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code computes drift/metrics, fingerprints revisions, freezes deployment, schedules authorized retraining, and verifies any new evaluation receipt.

**Code and governance own:** Data monitoring, drift calculation, training, retraining, deployment, version control, and business decisions.

**Simpler baseline:** Reuse the last feature-model result whenever a textual input pipeline changes.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H16's invalidation of one pending action after material state change and H20's human-adjudication confidence ledger, this is a feature-pipeline hold that binds question/data/policy revisions to held-out evidence.

## Limits and source

A stable receipt does not prove no real-world drift, and a hold does not identify the cause or corrective action.

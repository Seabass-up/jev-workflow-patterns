# E28: Classify dependency-upgrade intent

Read release-note language about a current integration without substituting it for compatibility tests.

## State contract

Supply a compact named JSON object with these required fields:

- <code>release_note</code>
- <code>current_integration</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>upgrade_intent</code>.

~~~json
{
  "upgrade_intent": {
"type": "choice",
"instructions": "What behavior intent is explicitly stated by release_note for the shown current_integration? Do not resolve versions, calculate compatibility, install a dependency, or infer a change absent from the note.",
"criteria": {
  "behavior_preserving": "The note explicitly describes the relevant change as a fix or maintenance change without a stated behavior/API change for the shown integration.",
  "opt_in_feature": "The note explicitly adds a feature that requires a named opt-in, new configuration, or new API use.",
  "stated_behavior_change": "The note explicitly deprecates, removes, changes defaults, changes an API contract, or otherwise states a behavior change relevant to the integration.",
  "insufficient": "The note/integration does not establish one listed intent."
}
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Bind the note to an exact version, run deterministic dependency and compatibility checks, and review unclear notes.

**Code and governance own:** Version resolution, install, dependency locking, compatibility tests, rollout, and rollback.

**Simpler baseline:** Read every release note manually before considering an upgrade.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike E03's proposed interface change against a consumer and E10's schema-rollout posture, this reads a third-party release note's stated intent before code tests the installed upgrade.

## Limits and source

Release notes can omit defects or migration details and never replace testing of the actual dependency.

# CY03 — Advisory names the product an asset description runs

[Cybersecurity catalog]({{ '/cybersecurity/' | relative_url }}) · [Evaluation and limitations]({{ '/cybersecurity/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/cybersecurity.md)

Classify whether a vulnerability advisory's affected-product text names the product an asset is described as running, or a component the description says it includes, so code can go on to compare versions.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/cybersecurity/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Filters the advisory feed by what each asset is described as running before exact version and build comparison in code, instead of a person reading every advisory against the inventory.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `advisory_affected_text`
- `asset_description`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `CY03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "advisory_affected_text": "Affected: Tessel TLS Library versions 2.4 through 2.9 when used to terminate HTTPS connections. Any product that embeds the affected library is affected; consult your product vendor for a list of embedding products.",
  "asset_description": "Marrow Mail Gateway, Standard edition, deployed as a virtual appliance at 192.0.2.40. It provides an HTTPS administration console and inbound mail filtering, and the inventory record states it includes the Pell anti-spam engine and the Larkspur attachment scanner."
}
```

Expected label: `no_named_match`.

The advisory names only the Tessel TLS Library, which is neither the asset's own product nor a component the asset description states it includes; the contract binds included_component_named to components the description states, not to what an appliance with an HTTPS console might plausibly embed.

## Code-owned responsibilities

Code compares affected version ranges, builds, and patch levels exactly, matches advisory and product identifiers against the inventory, and schedules remediation. The label only says whether the advisory names the product or an included component.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the inventory owner adds component detail to the asset description when the label is no_named_match and the advisory names a widely embedded component.

## Verification recipe

Run advisories with known affected-product lists against inventory descriptions with known outcomes; measure missed names per vendor naming style.

This describes required verification work, not checks already performed.

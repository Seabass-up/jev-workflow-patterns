# PM06 — Action item names an owner and a due expression

[Project management catalog]({{ '/project-management/' | relative_url }}) · [Evaluation and limitations]({{ '/project-management/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/project-management.md)

Check whether an action item, as written, names who will do it and states when it is due, without resolving the date.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/project-management/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Catches ownerless or undated actions before they leave the meeting; resolving 'by Friday' to a calendar date stays in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `action_item`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

```json
{
  "decision": {
    "type": "choice",
    "instructions": "First, if any required field (`action_item`) is absent, empty, or lacks the information needed for this judgment, select unknown before considering other labels. Classify whether `action_item` states an owner and a due expression. An owner is a named person or a specific role who will carry out the action; a group such as 'the team', 'someone', or 'everyone' is not an owner. A due expression is any stated time by which the action is to be done, such as a date, a weekday, 'before the demo', 'end of sprint', or 'by the next meeting'; words such as 'soon', 'as soon as possible', or 'when possible' are not a due expression. Do not resolve the expression to a date or judge whether it is realistic. Select owner_and_due_stated only when both an owner and a due expression are present; owner_only applies only when no due expression is stated, and due_only only when no owner is named.     "criteria": {

      "owner_only": "The item names a specific person or role but states no time by which it is to be done, or only a vague urgency word.",
      "due_only": "The item states a time by which it is to be done but names no specific person or role, or names only a group.",
      "neither_stated": "The item names no specific person or role and states no time by which it is to be done.",

    }
```

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `PM06-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "action_item": "Owner: TBD. Context: this came out of Sunita Rao's audit finding on the staging environment. Action: rotate the staging API keys and update the shared vault entry before the Thursday demo, as soon as possible ideally."
}
```

Expected label: `due_only`.

The owner field is a placeholder and Sunita is named only as the source of the finding, not as the person who will carry out the action, so no owner is named. 'Before the Thursday demo' is a stated time by which the action is to be done, and the vague 'as soon as possible' beside it does not remove that due expression.

## Code-owned responsibilities

Code resolves the due expression to a calendar date, matches the owner to the roster, and sends reminders; the label only reports what the item states.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; an item labeled owner_only, due_only, or neither_stated is returned to the meeting chair to complete.

## Verification recipe

Compare labels with the coordinator's action tracker for the same meetings; review each owner_and_due_stated label whose tracker row was left blank.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Action item](https://en.wikipedia.org/wiki/Action_item) (PM-S5). Describes an action item as a documented task that can be handled by a single person, typically assigned to someone who is then obligated to perform it and report back, and usually recorded in meeting minutes. Motivates PM06's owner and due expression check. Motivation only, not evidence of Jev performance.
- [Wikipedia: Minutes](https://en.wikipedia.org/wiki/Minutes) (PM-S4). States that the primary function of minutes is to record the decisions made, and that a summary of the discussions is distinct from the decisions themselves. Motivates PM05's decision-versus-discussion reading and PM06 and PM07 as readings of what recorded items and replies state. Motivation only, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

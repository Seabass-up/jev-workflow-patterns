# FN03 — Kind of payment-terms expression on a document

[Finance catalog]({{ '/finance/' | relative_url }}) · [Evaluation and limitations]({{ '/finance/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/finance.md)

Classify the kind of payment terms a document states so code can copy the expression and resolve the due date.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/finance/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Separates reading the terms clause from the date arithmetic and discount rules, which differ by vendor and stay in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `terms_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `FN03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "terms_text": "Terms: 30% deposit payable with order confirmation. The remaining 70% is due on receipt of the final invoice, which we issue on despatch. Late balances accrue interest at our standard rate."
}
```

Expected label: `installment_schedule`.

The wording states a deposit followed by a balance due later, which the contract explicitly assigns to installment_schedule; the phrase 'on receipt' governs only the second part and does not make the whole expression due_on_receipt.

## Code-owned responsibilities

Code copies the verbatim terms expression, parses the day count, resolves the due date against the invoice date and calendar, applies discount rules, and records the vendor terms revision.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; unknown or other_terms goes to accounts payable for manual coding.

## Verification recipe

Compare labels with the terms already coded on vendor records for paid invoices; review each mismatch against the document wording.

This describes required verification work, not checks already performed.

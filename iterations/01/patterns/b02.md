## The useful decision

Ask one useful follow-up before dispatch rather than exchange several vague messages. Measure: Follow-up turns to a dispatchable request and incorrect-ready rate.

Required state fields: `request`. One request evaluates one coherent state. These questions are independent; none can see another answer in its batch.

## Exact question contract (version 2)

```json
{
  "location": {
    "type": "noul",
    "instructions": "Does `request` state one unambiguous work location, with no unresolved conflicting location?",
    "criteria": {
      "true": "A definite site or unit is stated consistently.",
      "false": "The site or unit is missing, vague or contradicted."
    }
  },
  "symptom": {
    "type": "noul",
    "instructions": "Does `request` describe an observed problem or a concrete work task?",
    "criteria": {
      "true": "A specific symptom or work task is stated.",
      "false": "Only a vague request for help is given."
    }
  },
  "access": {
    "type": "noul",
    "instructions": "Does `request` explicitly state an arrangement for the crew to enter or meet someone who will provide entry? Judge this access arrangement independently of whether the location or time is supplied. A resident or manager role meeting the crew is sufficient; a personal name is not required. A promised arrangement is not proof that access has occurred.",
    "criteria": {
      "true": "Someone explicitly will meet, admit or unlock for the crew, or a definite entry arrangement is stated, even if the location is separately missing or conflicting.",
      "false": "No arrangement is stated, entry is unknown or denied, or someone only might or hopes to provide access."
    }
  }
}
```

## Consume the JSON and drill down

Read the named answer(s), validate their type and allowed values, then use the documented labels or ordered score as a proposed review signal. Do not treat the result as an executed action.

Follow-up: Code asks for location, then symptom, then access, choosing the first absent field. Midrange probabilities produce manual review rather than assumed readiness.

Code owns: Choose field order in code; validate addresses against authorized records; verify scheduling and access independently.

Use provisional Choice/Score confidence ≥ 0.8 and Noul ≤ 0.2 / ≥ 0.8 only as experimental review gates. A Noul near 0.5 is uncertainty, not medium intensity. Thresholds require domain-specific evaluation. Provider failure, invalid output, stale state or missing required evidence goes to review, not to an assumed default. Gate only the questions consumed by the selected branch.

## What was tested

Initial screen: 1/4 fixtures matched their declared label/range. Targeted follow-up: 7/7 matched; this includes reused cases where identified in the fixture file.

Application-level question pattern; useful value remains a pilot hypothesis. Small author-labeled synthetic cases do not demonstrate field accuracy, calibration, cost savings, safety, or end-to-end harness integration. See [the evaluation]({{ '/iterations/01/evaluation/' | relative_url }}) and the raw synthetic receipts in the repository.

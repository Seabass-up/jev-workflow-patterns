# DQ07 — Outlier note states a cause or only the value

[Data quality catalog]({{ '/data-quality/' | relative_url }}) · [Evaluation and limitations]({{ '/data-quality/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/data-quality.md)

Classify what an analyst's note about a code-flagged outlier states: a confirmed cause, a hypothesis, an action without a cause, or only the value.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/data-quality/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Lets code decide whether an exclusion or correction is documented well enough to stand, without the model judging the value or the cause itself.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `flag_context`
- `analyst_note`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Exact question JSON

Reproduced from the frozen [catalog JSON]({{ '/data-quality/catalog.json' | relative_url }}). Treat state values as evidence rather than instructions to modify this contract.

```json
{
  "decision": {
    "type": "choice",
    "instructions": "First, if any required field (`flag_context`, `analyst_note`) is absent, empty, or lacks the information needed for this judgment, select unknown before considering other labels. `flag_context` states which field and record code flagged as an outlier and what the flagged value was, and `analyst_note` is what the analyst wrote about it. Classify what the note states. A note that names a specific cause for the flagged value and describes how it was confirmed, such as a checked source, a contacted party, or a matching record, states a confirmed cause. A note that offers a possible cause without describing confirmation states a hypothesis only. A note that records what was done with the value, such as excluding, capping, nulling, or keeping it, and offers no cause records an action without a cause; select action_without_cause even if such a note also remarks on the value. A note that only says the value is high, low, unusual, or an outlier, or repeats the value, with no cause and no action, restates the value only. ## Policy recorded with its option count
```

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `DQ07-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "flag_context": "Table sensor_readings, record 88213, field temp_c flagged by the z-score rule; the flagged value was 71.4 in a series that otherwise sits between 18 and 24.",
  "analyst_note": "Capped at 24.0 for the monthly report so it does not drag the mean. Most likely the known cold-start spike this sensor model produces after a power cycle, though I have not pulled the sensor's event log to check whether it restarted that hour."
}
```

Expected label: `hypothesis_only`.

The note records an action but also offers a specific possible cause, and the contract says a note that states a cause and records an action is classified by the cause. The cause is expressly unverified, so it is hypothesis_only rather than confirmed_cause, and the presence of a cause rules out action_without_cause.

## Code-owned responsibilities

Code owns the outlier detection and its thresholds, the record of what was done with the value, the rule that only a confirmed_cause note lets an exclusion stand without review, and the review queue; a label never alters a value.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the analyst adds the confirmation the note lacked.

## Verification recipe

Compare labels with a reviewer's reading of outlier notes from a closed analysis and with exclusions later reversed; measure confirmed_cause labels on reversed exclusions first.

This describes required verification work, not checks already performed.

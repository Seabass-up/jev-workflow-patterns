# HA10 — Do not ask for the same answer again in different words

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Recognize when the next service question semantically repeats information the person already supplied for the same entity and time.

**Provisional:** the initial synthetic screen includes an unresolved label mismatch for this pattern. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Can reduce avoidable repetition without suppressing legitimate change checks or new information.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `previous_answer`
- `proposed_question`
- `reask_reason`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA10-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "previous_answer": "For Tuesday's workshop, reserve four chairs.",
  "proposed_question": "How many chairs should we reserve for Thursday's workshop? Do not include Tuesday's reservation.",
  "reask_reason": "none"
}
```

Expected label: `new_information`.

The repeated subject and quantity format do not make this redundant: the question explicitly requests a reservation for a different day.

## Code-owned responsibilities

Hold exact field/entity IDs, answer revisions, privacy scope, and required re-confirmation policies. Never suppress mandated re-entry or overwrite an earlier answer based solely on Jev.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

For unknown, obtain the field's entity/time definition once. For apparent redundancy, offer the already captured value for user confirmation only if the application permits it.

## Verification recipe

Use a test journey with recorded answers and inspect whether distinct entities and time periods stay separate. Compare suggested redundant questions with reviewer labels and count false suppression of needed questions.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [GOV.UK Design System: Question pages](https://design-system.service.gov.uk/patterns/question-pages/) (HC-S2). The guidance says to ask only needed questions, mark optional information, explain why questions are asked, accept uncertainty when valid, and avoid asking for the same information repeatedly within a journey. Patterns apply to known process rules rather than guessing whether personal data is necessary.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

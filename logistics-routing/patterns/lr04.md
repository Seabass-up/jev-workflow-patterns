# LR04 — Cause a driver's report gives for a route deviation

[Logistics routing catalog]({{ '/logistics-routing/' | relative_url }}) · [Evaluation and limitations]({{ '/logistics-routing/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/logistics-routing.md)

Classify which cause a driver states for deviating from the planned route, stop order, or schedule.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/logistics-routing/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Codes the day's deviations consistently for the log and the re-plan trigger, without treating the driver's account as verified fact.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `driver_report`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `LR04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "driver_report": "Tyre pressure light came on when I left the yard this morning but I checked it and it is fine, been fine all day. I ran late on stops 4 through 6 because Harrow Lane was shut for resurfacing and the signed detour loops out past the quarry road. Customers were all there and ready."
}
```

Expected label: `road_closure_or_detour`.

The warning light is mentioned but the driver explicitly does not attribute the deviation to it, and the contract says to use only the cause the driver states rather than one inferred from the report. The only stated cause is the closed road and posted detour, so the vehicle_problem tier of the precedence order is never reached.

## Code-owned responsibilities

Code computes the actual delay from telematics timestamps, re-plans the remaining stops, dispatches a replacement vehicle on its own rule, and records the driver's words unchanged; the label tags the report for the day's log.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a report the label calls unknown prompts a dispatcher message to the driver.

## Verification recipe

Compare labels with how dispatchers coded deviation causes for a month of reports, then with telematics and traffic data for the same trips.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Dispatcher](https://en.wikipedia.org/wiki/Dispatcher) (LR-S5). Describes dispatchers in trucking, courier, and other operations who relay information, direct personnel, and make real-time adjustments as conditions and delays change. Motivates LR01, LR03, LR04, and LR05 as readings of the notes, driver reports, and customer messages a dispatcher handles; the adjustment itself stays with the dispatcher and code. Motivation only, not evidence of Jev performance.
- [Wikipedia: Vehicle routing problem](https://en.wikipedia.org/wiki/Vehicle_routing_problem) (LR-S1). Describes routing as a computed optimization with variants for time windows at delivery locations, vehicle capacity, and pickup and delivery. Motivates LR01, LR02, LR03, LR04, LR05, and LR07 as readings of which constraint or preference a text states, with the solver computing distance, time, capacity, and sequence. Motivation only, not evidence of Jev performance.
- [FMCSA: Summary of Hours of Service Regulations](https://www.fmcsa.dot.gov/regulations/hours-service/summary-hours-service-regulations) (LR-S6). FMCSA summarizes driving-time limits, the 14-hour window, required breaks, weekly limits, sleeper-berth splits, the adverse-driving-conditions extension, and the short-haul exception for property-carrying drivers. Motivates LR02 and LR04 as readings of time-window and deviation text; every hours-of-service calculation and compliance decision stays in code and with the carrier.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

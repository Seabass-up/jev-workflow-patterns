# HA13 — Match a help route to the person's stated communication constraint

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Check whether one proposed human-help route accommodates an explicitly stated interaction constraint.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Can prevent sending a person back to a channel they have already said they cannot use.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `stated_constraint`
- `route_description`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA13-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "stated_constraint": "I can exchange asynchronous written messages, but I cannot attend a live chat or phone call.",
  "route_description": "Support replies to tickets by email, and no phone call is required. Before opening a ticket, however, the requester must join a live text chat with an agent to receive a ticket-access code; there is no asynchronous route to that code."
}
```

Expected label: `conflicting_route`.

The eventual email route fits the constraint, but its mandatory live-chat prerequisite explicitly conflicts with it. The whole route must be evaluated.

## Code-owned responsibilities

Resolve real channel URLs and hours, verify channel availability and accessibility, obtain permission before contacting anyone, and keep personal information out of public channels.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

If conflicting, inspect one already approved alternative route and compare it against the same explicit constraint; if none is compatible, report the gap without inventing an accommodation.

## Verification recipe

Inspect the actual support path to confirm whether an ostensibly online route ends in a required phone call. Test accessibility and availability separately; text describing compatibility is not proof that the service works.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [W3C WAI: Provide Human Help](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o7p01-human-help/) (HC-S4). The guidance recommends reachable human help through a mechanism the person prefers, with few steps and without complex menu navigation. The proposed pattern uses an explicitly stated interaction constraint and a supplied support route, never a disability or diagnosis inference.
- [GOV.UK Design System: Contact a department or service team](https://design-system.service.gov.uk/patterns/contact-a-department-or-service-team/) (HC-S7). The pattern recommends presenting supported contact channels according to user needs, showing availability and expected waits, and avoiding personal information on public social channels. The proposed route-compatibility check does not verify staff availability or contact any service.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question. Source summaries and recorded provenance are available in [sources JSON]({{ '/human-ai/sources.json' | relative_url }}); supplemental accessibility guidance is not a full conformance assessment.

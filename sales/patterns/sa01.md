# SA01 — What a prospect message asks for

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Classify what a prospect's message asks the seller to do so the right person or workflow answers it.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Routes inbound prospect messages by what they ask for instead of by keyword, while the account owner keeps the reply.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `prospect_message`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `SA01-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "prospect_message": "Thanks for all the time you put in over the last few weeks. We've signed a two-year agreement with Brightline, so we won't be moving forward with Lumen. That said, if your team would still run a short walkthrough of the reporting module for me, I'd like to see it so I know what to look for when the Brightline term comes up for renewal."
}
```

Expected label: `decline`.

The message states the prospect has chosen another option and will not proceed, which is a decline; the walkthrough ask is a demo_request, and the contract's precedence (decline before demo_request) selects decline.

## Code-owned responsibilities

Code owns the reply queue, the account owner assignment, and any automated quote; a pricing_request label never sends a price, and a decline label never closes the opportunity without a person.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

When the label is objection_raised, code passes the same message to SA02; no other follow-up call.

## Verification recipe

Compare labels with how the sales team actually handled a month of inbound prospect messages; review every decline and objection the label missed.

This describes required verification work, not checks already performed.

Describes designing a repeatable sales process from lead generation through closing and follow-up, with qualification criteria such as budget, authority, need, and timeline, standardised pipeline phases, and CRM pipeline management. Motivates SA03 (stated buying signals), SA05 and SA07 (follow-up and next-step records), and the pipeline framing of SA01 and SA02. Motivation only, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

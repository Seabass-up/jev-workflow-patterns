# E20: Classify cancellation boundary semantics

Make cancellation design review ask about effects before assuming a cancel is harmless.

## State contract

Supply a compact named JSON object with these required fields:

- <code>operation_plan</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>cancellation_semantics</code>.

~~~json
{
  "cancellation_semantics": {
    "type": "choice",
    "instructions": "What cancellation boundary is explicitly described by operation_plan? Classify the stated effect boundary only. Do not request cancellation, claim a compensating action works, or infer atomicity from a cancellation API.",
    "criteria": {
      "safe_before_effects": "The plan explicitly states cancellation occurs before any durable or externally visible effect.",
      "compensation_after_effects": "The plan explicitly states effects may occur and names a compensating or reconciliation path after cancellation.",
      "unsupported_or_unsafe": "The plan explicitly says cancellation is unsupported, ignored, or leaves effects without a stated recovery path.",
      "insufficient": "The plan does not establish one listed cancellation boundary."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Inspect callers, timeout behavior, and a failure-injection test before changing cancellation policy.

**Code and governance own:** Cancellation signals, transactions, compensation execution, cleanup, and runtime verification.

**Simpler baseline:** Assume cancellation means nothing happened.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike E11 rollback readiness, this concerns the semantic point at which an in-flight operation can stop and what happens to already-created effects.

## Limits, source, and shared skill

A plan description is not a demonstrated cancellation behavior.

# E21: Classify error-boundary ownership

Identify the explicitly stated layer responsible for translating or handling a failure before changing code.

## State contract

Supply a compact named JSON object with these required fields:

- <code>failure_description</code>
- <code>layer_catalog</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>owner</code>.

~~~json
{
  "owner": {
    "type": "choice",
    "instructions": "Which supplied layer in layer_catalog is explicitly stated to own translation or handling of the failure in failure_description? Select only a listed layer, no_explicit_owner, or insufficient. Do not infer a root cause, change an error handler, or choose a layer merely because it observes the error.",
    "criteria": {
      "caller": "The calling boundary is explicitly responsible for handling or translating the described failure.",
      "middleware": "A supplied middleware, transport, or framework boundary is explicitly responsible for handling or translating it.",
      "domain_service": "A supplied domain or application-service boundary is explicitly responsible for handling or translating it.",
      "no_explicit_owner": "The state explicitly says the responsibility is unassigned or omitted.",
      "insufficient": "The supplied description and catalog do not establish one listed responsibility."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Read the named boundary, callers, and tests before proposing a code change.

**Code and governance own:** Exception behavior, source resolution, logging, tests, and implementation changes.

**Simpler baseline:** Route every error to the nearest visible layer.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike E04's next diagnostic-source selection, this identifies a stated handling responsibility among code layers.

## Limits, source, and shared skill

Documentation may be stale and ownership does not prove a defect or authorize a code change.

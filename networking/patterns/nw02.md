# NW02 — Type of change a request describes

[Networking catalog]({{ '/networking/' | relative_url }}) · [Evaluation and limitations]({{ '/networking/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/networking.md)

Classify the type of network change a request describes so code can route it to the right approval path.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/networking/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Separates reading what a request says will change from the approval rule, which differs by change type and must stay in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `change_request`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `NW02-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "change_request": "Please update the internal zone so portal.example resolves to the new web tier at 198.51.100.20, and add a permit rule on the DMZ firewall allowing TCP 443 from the internet zone to that address. No hardware, cabling, or optics are involved, and the default route and existing VLAN assignments remain untouched."
}
```

Expected label: `firewall_policy_change`.

The request describes two change types, a DNS record update and a firewall permit rule, while physical and routing changes are explicitly negated rather than requested. Among the types actually described, the precedence order places firewall_policy_change before dns_record_change.

## Code-owned responsibilities

Code owns approval routing, blackout-window checks, exact device names and addresses, and every configuration line; the label never approves or generates a change.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the requester adds detail when the label is unknown.

## Verification recipe

Compare labels with the change type recorded by the change manager for a quarter of closed requests; review mismatches on requests that describe more than one type.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Change management (ITSM)](https://en.wikipedia.org/wiki/Change_management_(ITSM)) (NW-S2). Describes change management as the discipline that applies standardized methods and procedures to all changes to IT infrastructure so as to minimize related incidents, balancing the need for change against its potential impact. Motivates NW02 (change type for approval routing), NW05 (advisory-driven changes), and NW06 (runbook step reversibility); approval and execution stay with people and code. This is motivation for the patterns, not evidence of Jev performance.

# H34: Verbatim candidate-value normalization conveyor

Bind a code-found candidate span to a Jev selection and deterministic normalization without allowing model-generated values.

## State contract

Supply a compact named JSON object with these required fields:

- <code>document</code>
- <code>candidate_values</code>
- <code>requested_role</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>selected_candidate</code>.

~~~json
{
  "selected_candidate": {
"type": "choice",
"instructions": "Which supplied candidate_values entry, if any, plays requested_role in document? Select only a listed candidate or no_candidate. Do not invent a value, transpose characters, normalize it, or use an unlisted span.",
"criteria": {
  "candidate_1": "The first code-found candidate is explicitly the requested value.",
  "candidate_2": "The second code-found candidate is explicitly the requested value.",
  "no_candidate": "None of the supplied candidates is the requested value."
}
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code finds/deduplicates candidates, validates selection membership, copies the selected literal, normalizes it, and rejects malformed values.

**Code and governance own:** Regex/parser selection, candidate coverage, exact copying, normalization, validation, writes, and privacy controls.

**Simpler baseline:** Ask a generative model to emit a normalized value from raw text.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H14's offset-provenance extraction and L03's value meaning/entity validation, this controller enforces a closed candidate-to-output binding through code-side normalization.

## Limits and source

It cannot recover an omitted candidate or prove that code-side normalization is correct.

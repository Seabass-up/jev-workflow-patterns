# LR03 — Kind of direction a stop instruction gives the driver

[Logistics routing catalog]({{ '/logistics-routing/' | relative_url }}) · [Evaluation and limitations]({{ '/logistics-routing/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/logistics-routing.md)

Classify whether a stop instruction restricts the vehicle, directs handling of the goods, or names a contact, so code can file it in the right field.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/logistics-routing/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Catches vehicle restrictions that change the assignment before dispatch, instead of leaving them buried in free text the driver reads on arrival.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `stop_instruction`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `LR03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "stop_instruction": "No liftgate needed here, there is a proper dock. Text Priya on the number in the manifest when you are ten minutes out. Stack the cartons no more than four high on the left side of the receiving cage."
}
```

Expected label: `contact_instruction`.

The liftgate is mentioned only to say it is not required, so the text states no limit on which vehicle or equipment can serve the stop. It gives both a contact instruction and a handling instruction, and the contract's order selects contact_instruction before handling_instruction.

## Code-owned responsibilities

Code matches vehicle restrictions against the fleet's exact dimensions and equipment, assigns the vehicle, and stores contact details separately; the label only routes the text to the right field.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; unknown text is shown to the dispatcher with the stop.

## Verification recipe

Compare labels with the fields dispatchers filled in for the same stops; review every vehicle restriction the label missed, since those change the assignment.

This describes required verification work, not checks already performed.

# PM07 — Stakeholder reply approves, declines, acknowledges, or asks

[Project management catalog]({{ '/project-management/' | relative_url }}) · [Evaluation and limitations]({{ '/project-management/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/project-management.md)

Classify what a stakeholder's reply to a project request does: states agreement, states refusal, only acknowledges, or asks a question.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/project-management/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Keeps approvals from being logged on the strength of a 'thanks, received', and surfaces the questions that hold a request up.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `request_sent`
- `stakeholder_reply`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `PM07-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "request_sent": "Request to Ines Duarte, Director of Client Operations at Corvid Health.example: approve extending the Beacon intake pilot by three weeks so load testing can finish before go-live.",
  "stakeholder_reply": "Thanks for the thorough write-up, and I appreciate the team flagging this early rather than late. That said, I'm going to hold the pilot at its current end date; three more weeks isn't something I can support this quarter given the board commitment. Happy to revisit in January if the picture changes. Could you send me whatever load-test results you already have by Friday?"
}
```

Expected label: `declines`.

Holding the pilot at its current end date and saying the extension cannot be supported states refusal of what was asked, so the reply declines even though it opens with thanks and offers to revisit later. The closing question does not change the label because the contract selects declines when a reply declines and also asks a question.

## Code-owned responsibilities

Code checks that the replying stakeholder holds the authority the request needs, records any stated condition with the reply's exact wording, and updates the request's status; the label does not grant approval.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; an unknown label leaves the request open for the project manager.

## Verification recipe

Compare labels with the project manager's own reading of a quarter of stakeholder replies; review each approves label the manager did not treat as approval.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Minutes](https://en.wikipedia.org/wiki/Minutes) (PM-S4). States that the primary function of minutes is to record the decisions made, and that a summary of the discussions is distinct from the decisions themselves. Motivates PM05's decision-versus-discussion reading and PM06 and PM07 as readings of what recorded items and replies state. Motivation only, not evidence of Jev performance.
- [Wikipedia: Change control](https://en.wikipedia.org/wiki/Change_control) (PM-S3). Describes change control as a process of plan and scope, assess, review and approval, build, implement, and close steps so that changes are introduced in a controlled way. Motivates PM03's separation of scope changes from clarifications and PM07's reading of approval replies. Motivation only, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

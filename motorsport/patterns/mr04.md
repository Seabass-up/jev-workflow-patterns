# MR04 — Finding statement is a conformance claim, an observation, or a recommendation

[Motorsport catalog]({{ '/motorsport/' | relative_url }}) · [Evaluation and limitations]({{ '/motorsport/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/motorsport.md)

Classify what kind of statement a finding makes so that conformance claims are verified in code before anyone acts on them.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/motorsport/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Separates statements that assert pass or fail from statements that merely report or propose, so no claimed conformance enters a record without an exact check.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `finding_statement`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `MR04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "finding_statement": "Plank thickness at the rear reference hole measured 8.6 mm with the depth micrometer after the session; the tolerance sheet lists a 9.0 mm minimum at that hole. Photographs and the raw reading are attached for the scrutineers' file."
}
```

Expected label: `observation`.

The statement reports the measured value and quotes the limit side by side but never asserts that the plank is within or outside it, passes or fails, and proposes no action; the comparison of the two numbers is code's job, so the statement remains an observation.

## Code-owned responsibilities

Code re-checks every conformance_claim against the stored value, tolerance, and unit before it is accepted, records who made the claim, and routes recommendations to the engineer who decides; the label never confirms a claim.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; an unknown statement is returned to its author for rewording.

## Verification recipe

Compare labels with how the quality lead tagged a season of finding statements; review every conformance_claim the label filed as an observation.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Engineering tolerance](https://en.wikipedia.org/wiki/Engineering_tolerance) (MR-S3). Defines a tolerance as the permissible limit of variation, notes that tolerances can be applied to any dimension or physical property, and that a part outside tolerance is unusable by design intent while a stated tolerance does not by itself imply compliance. Motivates MR03 (which property is constrained), MR04 (a conformance claim is distinct from an observation), and MR07 (dimensional and mass notes). Motivation only, not evidence of Jev performance.
- [NIST: Measurement Uncertainty (Statistical Engineering Division topic page)](https://www.nist.gov/itl/sed/topic-areas/measurement-uncertainty) (MR-S2). States that a measurand has a numerical magnitude and a reference that gives that magnitude meaning, and that uncertainty characterises the dispersion of values attributable to it. Motivates MR01 (a reference must be stated), MR02 and MR04 (a value is not a result until compared in code), MR03 (the property must be identified before its limit is applied), and MR08 (a prediction needs a named quantity). Motivation only, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

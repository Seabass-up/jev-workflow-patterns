# H24: Atomic score composition with veto policy

Keep semantic dimensions reusable while code decides which preferences may compensate and which failures must veto.

## State contract

Supply a compact named JSON object with these required fields:

- <code>candidate</code>
- <code>evaluation_rubric</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract (v3)

Question IDs: <code>fit</code>, <code>operational_burden</code>, <code>named_veto</code>, <code>burden_available</code>.

~~~json
{
  "fit": {
    "type": "score",
    "instructions": "Rate how well candidate fits the stated desired outcome in evaluation_rubric. Judge only supplied semantic fit; do not decide the final policy outcome. Assess desired-outcome fit independently of operational burden and the named-veto condition. A triggered veto does not reduce this fit score when the stated desired outcomes are fulfilled; code handles the veto separately.",
    "criteria": [
      "No demonstrated fit.",
      "Limited fit with important unmet desired outcomes.",
      "Strong fit for the stated desired outcome."
    ]
  },
  "operational_burden": {
    "type": "score",
    "instructions": "Rate the operational burden explicitly stated for candidate under evaluation_rubric. Do not invent cost, timing, or resources. This numeric output is usable only when code accepts the independent burden_available signal; when burden evidence is missing or conflicting, code ignores this score rather than treating it as low burden.",
    "criteria": [
      "Low stated burden.",
      "Moderate stated burden.",
      "High stated burden."
    ]
  },
  "named_veto": {
    "type": "noul",
    "instructions": "Does candidate explicitly trigger a non-compensable veto condition named in evaluation_rubric?",
    "criteria": {
      "true": "A named veto condition is directly met by the supplied candidate.",
      "false": "No named veto condition is directly met by the supplied candidate."
    }
  },
  "burden_available": {
    "type": "noul",
    "instructions": "Does candidate provide enough explicit, relevant operational-burden evidence under evaluation_rubric to assign a stated burden level meaningfully? Judge only whether burden evidence is available and interpretable for this candidate, not whether the burden is low. A missing burden statement, burden for another candidate only, or materially conflicting statements without a controlling resolution does not establish availability. Do not infer burden from feature fit or from absence of a veto. An explicit qualitative statement that this candidate has low, moderate, or high operational burden counts as available evidence under a rubric with those levels; no numeric measurement, resource breakdown or justification is required for this availability judgment.",
    "criteria": {
      "true": "Relevant explicit burden information supports an interpretable rubric level, including a directly stated qualitative low/moderate/high level without numeric measurements.",
      "false": "Burden evidence is absent, irrelevant to this candidate, or materially conflicting without a resolution."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code preserves a named-veto review first. Otherwise it uses a provisional burden_available >= 0.8 gate before any weighted-score proposal; unavailable or uncertain burden requires review and the burden score is ignored. One follow-up may request the missing burden evidence; no rewording until a preferred score appears.

**Code and governance own:** Weights, thresholds, veto policy, numeric calculation, source identity, and all action decisions.

**Simpler baseline:** Ask one opaque question such as whether a candidate is good overall.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H19's policy hazard/severity routing matrix, this generalizes code-owned weighted preference with an explicit non-compensable veto across independent score dimensions.

## Limits, source, and shared skill

## Local review: availability before score composition

The consumer preserves a named-veto review first; otherwise it requires the provisional `burden_available >= 0.8` gate before proposing score composition. Missing, irrelevant, conflicting or uncertain burden evidence routes to review, and the burden score is ignored. A Score is never evidence that a quantity was supplied.

Original v1 evidence is preserved in `results/h24-pre-review-contract.json`. The v2 screen preserves three misses; one bounded v3 refinement matched 6/7 cases and 27/28 question intervals. The negated-extra-resources case remains at availability 0.66 versus its frozen 0.8–1 interval and therefore returns review, not calculation. No threshold, expected interval or state was changed to hide the miss. These are synthetic development checks, not production qualification.

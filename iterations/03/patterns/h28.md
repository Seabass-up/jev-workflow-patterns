# H28: Bounded speculative fan-out scheduler

Batch independent work while preventing stale or inapplicable speculative branches from driving an action.

## State contract

Supply a compact named JSON object with these required fields:

- <code>state_snapshot</code>
- <code>question_manifest</code>
- <code>budget</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>batch_status</code>.

~~~json
{
  "batch_status": {
    "type": "choice",
    "instructions": "What batching status is supported by state_snapshot, question_manifest, and budget? Classify only whether the listed questions can share one immutable state evaluation. Do not execute a question, infer a missing premise, or reuse an answer after state changes.",
    "criteria": {
      "batchable": "All listed questions are explicitly independent, name their premises, fit the stated budget, and target the same immutable snapshot.",
      "dependent_sequence_required": "At least one listed question explicitly needs an earlier answer or a state fetch before it can be meaningfully asked.",
      "over_budget_or_oversized": "The manifest explicitly exceeds a stated question, byte, cost, or latency budget.",
      "stale_or_unverifiable_snapshot": "The state snapshot is explicitly stale, changed, or cannot be tied to the question manifest."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code batches only batchable questions, sequences dependencies, stamps snapshot IDs, and drops answers for stale branches.

**Code and governance own:** Limits, serialization, request construction, cache scope, concurrency, cost, latency, and answer consumption.

**Simpler baseline:** Send a separate request for every question or batch dependent questions blindly.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H12's repeated-decision stability gate, this controls which independent questions share one immutable request and how code discards stale speculative answers.

## Limits, source, and shared skill

Batching does not create cross-question reasoning or prove that a branch is relevant.

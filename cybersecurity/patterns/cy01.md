# CY01 — What a user-reported email asks the recipient to do

[Cybersecurity catalog]({{ '/cybersecurity/' | relative_url }}) · [Evaluation and limitations]({{ '/cybersecurity/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/cybersecurity.md)

Classify which of four asks a user-reported email makes, so the phishing-response queue routes it to the matching playbook.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/cybersecurity/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Sorts the report queue by the ask the message actually makes instead of by the reporter's guess, while sender checks, quarantine, and finance notification stay with code and the analyst.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `reported_message`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `CY01-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "reported_message": "Subject: New voicemail (0:47) is ready. Visible sender: Unified Messaging Service <notifications@voice-portal.example>. Body: You have one new voicemail from an external caller. To listen, open the attached file Voicemail_0047.html and sign in with your mailbox password when prompted; the recording is removed after 24 hours. Attachments: Voicemail_0047.html. Links: none."
}
```

Expected label: `sign_in_detail_request`.

The message both urges the recipient to open an attached voicemail file and asks for the mailbox password in the attached form; the contract's precedence order puts sign_in_detail_request ahead of attachment_open_request, and the attachment_open_request criterion applies only when no sign-in detail is requested.

## Code-owned responsibilities

Code checks the sender domain, link hosts, and attachment hashes against block and allow lists, records the reporter and message identifiers, and applies the response playbook for each label. The label never decides that a message is malicious or safe; quarantine, sender blocking, and notifying finance are analyst actions.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a none_of_these label with an attachment name still goes through the standing attachment scan in code.

## Verification recipe

Compare labels with the analyst's final disposition on a month of reported messages; measure payment change and sign-in detail requests the label filed as none_of_these first.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Phishing](https://en.wikipedia.org/wiki/Phishing) (CY-S2). Encyclopedic overview of messages that pose as trusted senders to obtain sign-in details, deliver harmful attachments, or redirect payments, and of the user-reporting channels organizations run. Motivates CY01 as a classification of the ask a reported message makes; it is motivation for the design, not evidence of Jev performance, and no technique is reproduced in the contract.
- [NIST SP 800-61 Rev. 3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management (CSRC publication page)](https://csrc.nist.gov/pubs/sp/800/61/r3/final) (CY-S1). Describes incident response as detection and analysis of events, prioritization by impact, and coordination with other risk-management activities. Motivates CY02 (an alert narrative against its stated context), CY04 (a report against a severity definition), and CY07 (log events as detection input) as text classifications within that workflow. This is motivation for the pattern designs, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

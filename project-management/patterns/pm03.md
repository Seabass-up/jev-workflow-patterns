# PM03 — Change request alters scope or clarifies it

[Project management catalog]({{ '/project-management/' | relative_url }}) · [Evaluation and limitations]({{ '/project-management/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/project-management.md)

Classify what kind of request a change form makes against the approved scope statement: a change to what is delivered, a clarification of what the scope already says, a defect against it, or a change only to timing or people.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/project-management/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Keeps the change board's queue to real scope changes and lets clarifications be answered from the scope statement, without the model deciding approval.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `change_request`
- `scope_statement`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `PM03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "change_request": "CR-118 from Marisol Vega, Account Management. Type selected on the form: Defect. The export is unusable for my team: it only produces CSV, and the finance template we paste into requires XLSX with a bolded header row. Please fix the export so it produces XLSX. No change to timing or staffing is requested.",
  "scope_statement": "Project Tidewater delivers a monthly usage report for account managers. Acceptance criteria: (1) the report can be exported as CSV from the reports page; (2) exports complete within 60 seconds for accounts up to 10,000 rows; (3) column headers match the data dictionary v3."
}
```

Expected label: `scope_change`.

The delivered CSV export is exactly what the scope statement's acceptance criterion requires, so the work does not fail the scope and the request is not a defect report despite the form's Defect label. Asking for XLSX output alters an acceptance criterion so the result would differ from the scope, and scope_change ranks first in the contract's precedence order.

## Code-owned responsibilities

Code routes scope_change to the change board with the request identifier and scope revision, records the board's decision, and computes any cost or schedule effect; the label never approves a change.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One clarification request to the requester when the label is unknown.

## Verification recipe

Compare labels with how the change board dispositioned a quarter of requests; review each clarification label the board treated as a scope change.

This describes required verification work, not checks already performed.

# HA16 — Do not promise a capability the assistant does not have

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Check prospective capability wording against the actual capabilities supplied by the application.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Can prevent users from relying on a draft-only or read-only assistant to perform an action it cannot carry out.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `capability_contract`
- `introductory_promise`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA16-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "capability_contract": "The assistant can assemble a draft support ticket and save it in a local review queue. It cannot transmit tickets to the support service, even after a person reviews a draft.",
  "introductory_promise": "I can assemble the ticket and save it for your review. After you review it, I will automatically transmit it to the support service."
}
```

Expected label: `capability_overpromised`.

The drafting and review-queue promises are supported, but the later transmission promise describes an operation explicitly excluded by the contract. Review does not add that missing capability.

## Code-owned responsibilities

Own tool discovery, installed capabilities, permissions and actual execution. Keep the contract current and bind it to the product revision; a model match is not an authorization or completion receipt.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

If overpromised, inspect one exact capability definition to resolve ambiguity and revise wording for review; never add permissions merely to make the promise true.

## Verification recipe

Inspect the actual enabled tool/API surface and permissions, then test the user-visible start message against those capabilities. Evaluate whether people understand the limitation with usability tests.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [Microsoft Research: Guidelines for human-AI interaction design](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/) (HC-S6). The researchers' official summary describes capability disclosure, efficient correction, granular feedback, consequences of user actions, and global controls. It reports that the guidelines were developed and tested for graphical products, not a Jev effectiveness benchmark or blanket voice-interface result.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

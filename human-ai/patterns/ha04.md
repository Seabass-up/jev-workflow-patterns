# HA04 — Feedback judges the person instead of the work

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Classify whether feedback offers task/process guidance or only a general judgment of the learner.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Helps AI tutors revise feedback into something the person can use without labeling their ability.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `task_context`
- `feedback_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA04-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "task_context": "Feedback on a draft set of instructions for assembling a paper model.",
  "feedback_text": "The opening diagram does a good job of showing the fold direction. The next diagram omits the tab label; add that label, then check that every label in the written steps appears in a diagram."
}
```

Expected label: `learning_directed`.

The praise explicitly concerns a diagram's work, and the remaining text supplies a correction and a checking strategy. No general claim about the person or their ability appears.

## Code-owned responsibilities

An educator or host edits feedback and checks subject correctness. Code does not turn this label into grading, personality assessment, or a persistent learner trait.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

Offer one revised feedback draft for human review; never generate or store an ability diagnosis.

## Verification recipe

Human-review feedback examples with neutral praise, mixed guidance, and task corrections; measure usefulness with consenting users separately.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [What might the content of effective feedback look like in the classroom?](https://d2tic4wvo1iusb.cloudfront.net/production/eef-guidance-reports/feedback/Effective_Feedback_Task__Subject_and_Self-regulation_Strategies.pdf) (HL-S4). EEF distinguishes feedback directed at work, subject processes, or self-regulation from general comments about a person's characteristics. It notes boundaries between productive categories can blur; the proposed question does not force those subcategories.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

# HA19 — Does a recommendation disclose its tradeoff?

[Human + AI catalog]({{ '/human-ai/' | relative_url }}) · [Evaluation and limitations]({{ '/human-ai/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-ai.md)

Check whether a recommendation acknowledges a stated downside that matters to the user's explicit priorities.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-ai/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Give the person a real choice instead of presenting one option's advantage as if it has no relevant cost.

This is a proposed benefit, not an observed human outcome. All fixtures on this page are synthetic. No study with people was conducted for this catalog, and the question must not be used to infer a person's traits, ability, diagnosis, or intent.

## Required named state

Supply the following named fields as the evidence packet:

- `user_priorities`
- `option_facts`
- `recommendation`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. Preserve the exact source revision. Any remaining insufficiency or ambiguity follows the question's `unknown` criteria; a model label cannot establish missing facts.

## Complete synthetic example

This is fixture `HA19-4`, from the **challenge** split. Its author received the question contract without the original design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "user_priorities": "Compare only storage capacity and how heavy the empty cases are to carry.",
  "option_facts": "Case A and Case B each hold the same 20 tools and each weighs 2 kilograms empty. A is orange; B is gray. The orange finish scratches more easily.",
  "recommendation": "Choose Case A. It meets the requested storage and carrying requirements just as well as B. Its orange color also makes it easy to spot."
}
```

Expected label: `no_stated_tradeoff`.

The supplied disadvantage concerns finish durability, not either named priority. Equal capacity and weight establish no tradeoff on the requested dimensions.

## Code-owned responsibilities

Verify option identities, facts and freshness; do exact numerical comparisons outside Jev. The user chooses priorities. Preserve all alternatives and never treat the label as endorsement.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

If a tradeoff is hidden, add one concise benefit-versus-sacrifice statement grounded in the supplied facts; request a priority choice only when it changes the next step.

## Verification recipe

Use human-reviewed comparison packets; check every named tradeoff against underlying option evidence and verify visible recommendation text preserves it.

This describes required verification work, not checks already performed. Separate agreement with synthetic expected labels from successful execution of the real workflow and from any measured benefit to a person.

## Source inspiration

- [Google PAIR: User Needs + Defining Success](https://pair.withgoogle.com/chapter/user-needs/) (HD-S2). Official design guidance distinguishes augmentation from replacing work people want to do, and warns that narrow reward functions can miss broader outcomes. These are design principles, not empirical Jev performance claims.
- [Google PAIR: Explainability + Trust](https://pair.withgoogle.com/chapter/explainability-trust/) (HD-S6). Official guidance discusses what and when to explain, the limits of explanations, and calibrated trust. It motivates matching the explanation to the person's explicit question, not inventing model reasoning.
- [To Trust or to Think (Buçinca, Malaya and Gajos, CSCW 2021)](https://www.eecs.harvard.edu/~kgajos/papers/2021/bucinca2021trust.shtml) (HD-S8). An original experiment found a tradeoff between overreliance reduction and participants' subjective ratings of cognitive-forcing designs. Explanations alone did not establish appropriate reliance. This is a limitation on simplistic help-quality claims, not a prescription to force extra steps.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question. Source summaries and recorded provenance are available in [sources JSON]({{ '/human-ai/sources.json' | relative_url }}); supplemental accessibility guidance is not a full conformance assessment.

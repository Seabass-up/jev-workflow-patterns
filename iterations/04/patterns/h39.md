# H39: Literal-boundary contract fixture controller

Exercise a new question's negations, exclusions, no-evidence cases, and conflicts before it is used as an application contract.

## State contract

Supply a compact named JSON object with these required fields:

- <code>question_contract</code>
- <code>boundary_fixture</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>boundary_status</code>.

~~~json
{
  "boundary_status": {
"type": "choice",
"instructions": "Under question_contract, how does boundary_fixture relate to the stated condition and criteria? Read the literal wording. Do not rewrite the contract, change expected labels, invoke a production action, or infer an unstated exception.",
"criteria": {
  "explicit_pass": "The fixture explicitly satisfies the condition/criteria for the intended positive or selected outcome.",
  "explicit_fail": "The fixture explicitly negates or excludes the condition/criteria for the intended positive or selected outcome.",
  "contradictory": "The fixture exposes incompatible instruction/criteria statements or conflicting stated conditions.",
  "uncovered": "The contract does not clearly state how this boundary fixture should be classified."
}
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code freezes fixtures/expected labels before live calls, verifies no labels leak into state, versions revisions, and requires owner review for uncovered/contradictory cases.

**Code and governance own:** Fixture generation, label adjudication, contract editing, regression testing, and release policy.

**Simpler baseline:** Publish a question contract after only happy-path examples.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H05's repair after one observed question defect and H12's repeated-decision stability gate, this is a preventative literal-wording fixture controller that preserves unresolved contract boundaries.

## Limits and source

Synthetic fixtures cannot cover all language ambiguity or establish production behavior.

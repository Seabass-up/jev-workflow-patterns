# LC02 — Which named party a clause obligates

[Contracts catalog]({{ '/legal-contracts/' | relative_url }}) · [Evaluation and limitations]({{ '/legal-contracts/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/legal-contracts.md)

Classify which of the two named parties a clause places an obligation on, using the party names exactly as supplied.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/legal-contracts/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Builds an obligations register by party without a person re-reading every clause; the lawyer confirms the register.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `clause_text`
- `party_a`
- `party_b`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `LC02-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "clause_text": "Harbor Analytics may, at its election and not more than twice in any calendar year, request an on-site inspection of the Facility. Upon receipt of such a request, Northgate Supply shall admit Harbor Analytics' designated representatives during normal business hours and shall make available the production records for the preceding quarter. Nothing in this Section obliges Harbor Analytics to conduct any inspection or to give reasons for requesting one.",
  "party_a": "Harbor Analytics",
  "party_b": "Northgate Supply"
}
```

Expected label: `obligation_on_party_b`.

Harbor Analytics receives only a permission ("may"), while "shall admit" and "shall make available" are requirements directed at Northgate Supply; the closing sentence confirms that nothing is required of Harbor Analytics, so Northgate Supply alone is bound.

## Code-owned responsibilities

Code supplies the party names exactly as the agreement defines them, keys the register by clause number, and routes clauses that name a third party to a person; the label never decides whether an obligation was met.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after code substitutes the agreement's defined party labels for the parties' full names when the label is unknown.

## Verification recipe

Compare labels with an obligations register a paralegal built by hand for a set of agreements; review every clause the register assigns differently.

This describes required verification work, not checks already performed.

## Source inspiration

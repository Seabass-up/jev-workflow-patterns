# LG03 — Customs document type from its text

[Logistics catalog]({{ '/logistics/' | relative_url }}) · [Evaluation and limitations]({{ '/logistics/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/logistics.md)

Classify whether a document's text is a commercial invoice, a packing list, a certificate of origin, or another shipping document.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/logistics/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Files inbound customs paperwork under the right document type before a broker or coordinator checks its contents; values, codes, and completeness are checked in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `document_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Exact question JSON

Reproduced from the frozen [catalog JSON]({{ '/logistics/catalog.json' | relative_url }}). Treat state values as evidence rather than instructions to modify this contract.

```json
{
  "decision": {
    "type": "choice",
    "instructions": "First, if any required field (`document_text`) is absent, empty, or lacks the information needed for this judgment, select unknown before considering other labels. Classify the type of shipping document that `document_text` is, from its own content and headings. If the text states unit prices, a currency, or a total value for the goods, select commercial_invoice even when it also lists package weights, dimensions, or a country of manufacture. If it itemizes cartons or packages with contents, counts, weights, or dimensions and states no prices, select packing_list. Select certificate_of_origin only when the text's purpose is to attest or certify the country where the goods originate; an origin line inside an invoice or packing list does not make it a certificate. Do not check whether the document is complete or correct.       "certificate_of_origin": "The text declares or certifies the country in which the listed goods were produced, typically with an attestation by the exporter, a chamber, or an authority.",
      "other_document": "The text is a shipping or customs document of a kind other than the three listed types, such as a bill of lading, an airway bill, or a declaration form.",
```

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `LG03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "document_text": "PACKING LIST AND ORIGIN DECLARATION, ref PL-EX-3308, shipper Tallow Fabrication Ltd. (tallowfab.example), consignee Brindle Retail Co. (brindle.example). Carton 1 of 3: 40 steel brackets model SB-9, gross 18 kg, 60x40x30 cm; carton 2 of 3: 40 steel brackets model SB-9, gross 18 kg, 60x40x30 cm; carton 3 of 3: 12 mounting kits MK-2, gross 6 kg, 40x30x20 cm. Total 3 cartons, gross 42 kg. The undersigned exporter declares that the goods described above were wholly produced in the Republic of Exampleland. Signed T. Varga, Export Manager."
}
```

Expected label: `packing_list`.

The text itemizes cartons with contents, counts, weights, and dimensions and states no prices, currency, or value, so the packing_list rule applies. It also carries an exporter's origin attestation, but when a text combines elements of more than one listed type the contract's order selects packing_list before certificate_of_origin.

## Code-owned responsibilities

Code validates the required fields for each document type, checks tariff codes, values, and totals exactly, matches the document to the shipment, and leaves classification of the goods and any declaration to the customs broker.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; other_document and unknown go to the broker's inbox with the file attached.

## Verification recipe

Run a set of documents with known types through the check; measure confusion between invoice and packing list on documents that list both weights and prices.

This describes required verification work, not checks already performed.

## Source inspiration

- [Wikipedia: Commercial invoice](https://en.wikipedia.org/wiki/Commercial_invoice) (LGS-2). Describes the commercial invoice as a customs document that identifies the parties, the goods, the country of manufacture, and tariff codes, and distinguishes it from an invoice for payment and from a packing list. Motivates LG03: the model classifies the document's type from its text, and code validates its fields. Motivation only, not evidence of Jev performance.
- [Wikipedia: Certificate of origin](https://en.wikipedia.org/wiki/Certificate_of_origin) (LGS-3). Defines a certificate or declaration of origin as a document attesting that listed goods originate in a particular country, prepared by the exporter or manufacturer and often certified by a chamber of commerce or authority. Motivates the certificate_of_origin label in LG03 and its rule that an origin line inside another document is not a certificate. Motivation only, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

# HR06 — Offer letter states every required element

[Human resources catalog]({{ '/human-resources/' | relative_url }}) · [Evaluation and limitations]({{ '/human-resources/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-resources.md)

Check whether an offer letter states each element the organization's checklist requires, such as title, start date, compensation, and contingencies.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-resources/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Catches a merged template that dropped or doubled an element before the letter is sent; the values themselves and the approval stay with people and code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `offer_letter_text`
- `required_elements`

Consumer code must deterministically return `unknown` without invoking Jev when any required named field is absent or empty; this collection does not implement or verify that gate. The live missing-input case below probes the contract wording, not that gate.

```json
    "criteria": {

      "missing_elements": "At least one listed element is given no value in the letter, and no listed element is given two different values.",
      "inconsistent_elements": "At least one listed element is given two different values, whether or not another listed element is given no value.",

```

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is reviewer-authored regression fixture `HR06-5`, added after an earlier boundary finding to test the revised contract. Its expected label was recorded before the current screen; it is not an independent or held-out case.

```json
{
  "offer_letter_text": "Dear Alex, we offer the role of Dispatch Coordinator, reporting to Lena, Operations Manager. Your start date is November 10, 2026. Your base salary is $58,000 per year, paid biweekly. This offer is contingent on a satisfactory background check. Compensation summary: annual base salary $56,000.",
  "required_elements": [
    "job title",
    "start date",
    "base salary",
    "reporting manager",
    "contingencies"
  ]

```

Expected label: `inconsistent_elements`.

Every checklist item is stated, but base salary has two different values; the contract selects inconsistent_elements.

## Code-owned responsibilities

Code holds the checklist per letter template and jurisdiction, compares the stated values with the approved offer record exactly, and controls who may send the letter. The label never approves an offer.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the recruiter revises the letter.

## Verification recipe

Run past letters with known omissions through the check; measure missed omissions per template before measuring anything else.

This describes required verification work, not checks already performed.

# B21: Classify recurring service trigger language

Separate a recurring service rule from the deterministic schedule calculation it enables.

## State contract

Supply a compact named JSON object with these required fields:

- <code>service_plan</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>service_trigger</code>.

~~~json
{
  "service_trigger": {
    "type": "choice",
    "instructions": "What service trigger is explicitly described by service_plan? Classify the recurrence language only. Do not calculate a next date, infer usage, decide contractual scope, or schedule a visit.",
    "criteria": {
      "one_time": "The plan describes a single non-recurring service occurrence.",
      "calendar_interval": "The plan states recurrence by a calendar interval such as monthly, quarterly, or annually.",
      "usage_or_condition": "The plan states recurrence based on observed use, a meter, a condition, or a threshold.",
      "event_triggered": "The plan states recurrence after a named event rather than a calendar interval or usage level.",
      "unclear": "The supplied plan does not establish one listed trigger."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Ask the service owner to resolve unclear rules; use verified source data and deterministic code for next-occurrence computation.

**Code and governance own:** Date arithmetic, meter processing, scope, dispatch, and customer communication.

**Simpler baseline:** Treat every maintenance sentence as a manual scheduling task.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike B14, this classifies the recurrence rule that governs future service rather than finding one deadline expression in a message.

## Limits, source, and shared skill

It does not confirm that a visit is due, authorized, or feasible.

# FN04 — Variance explanation names a cause or restates the number

[Finance catalog]({{ '/finance/' | relative_url }}) · [Evaluation and limitations]({{ '/finance/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/finance.md)

Check whether budget-versus-actual commentary states a driver for the variance or only repeats it.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/finance/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Returns empty commentary to the line owner before the review meeting, while the variance itself is computed and checked in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `variance_line`
- `explanation_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

```json
    "criteria": {

      "restates_variance": "The explanation repeats the amounts, the direction, or the percentage without saying what produced them.",
      "defers_explanation": "The explanation says the cause is being investigated or will be provided later and states no driver.",
      "unknown": "Required evidence is missing, contradictory, or does not support a determinate classification."
    }
  }

```

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `FN04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "variance_line": "Account 6210 Contract labour, cost centre Field Services: actual spend for August was above budget (unfavourable).",
  "explanation_text": "Contract labour came in over budget for August because costs in this account were higher than the amount we planned. The overspend is unfavourable and is concentrated in the Field Services cost centre, consistent with the ledger. The budget figure itself was set correctly and does not need to change."
}
```

Expected label: `restates_variance`.

Despite the causal wording 'because', the text only says spend was higher than planned and repeats the direction and location of the variance; it names no event, decision, volume change, price change, or timing shift that produced it, and it does not say the cause is under investigation.

## Code-owned responsibilities

Code computes and states the variance, checks any amounts the commentary quotes against the ledger, and decides which lines require commentary; the label only flags commentary that explains nothing.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the line owner submits revised commentary when the label is restates_variance or defers_explanation.

## Verification recipe

Compare labels with the FP&A reviewer's accept-or-return decision on one close cycle's commentary; review every explanation the label accepted that the reviewer returned.

This describes required verification work, not checks already performed.

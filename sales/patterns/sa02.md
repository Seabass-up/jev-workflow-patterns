# SA02 — Which kind of objection the prospect raises

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Classify a stated sales objection by its kind so the right response material and owner are used.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Separates price, timing, authority, and need objections consistently so responses match the concern rather than the rep's guess.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `objection_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `SA02-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "objection_text": "Budget-wise it's a stretch this year, but honestly that isn't the real blocker. Most of what you showed overlaps with what we already run in Ledgerly, and the team is comfortable with it. Even if that changed, I'd need Priya to sign off before anything moved."
}
```

Expected label: `need_objection`.

Three kinds are stated: price (a stretch), need (already has a working solution in Ledgerly), and authority (Priya must sign off); the contract's order puts need_objection first regardless of which one the writer calls the real blocker.

## Code-owned responsibilities

Code selects the response material for each label, records the objection on the opportunity, and leaves any pricing concession or timeline change to the account owner and their manager.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; an other_objection label goes to the account owner for reading, not another model call.

## Verification recipe

Compare labels with objection categories the sales team recorded manually on closed opportunities; review disagreements on messages that state two concerns.

This describes required verification work, not checks already performed.

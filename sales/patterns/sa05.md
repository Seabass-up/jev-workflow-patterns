# SA05 — How a follow-up commitment names its time

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Classify whether a follow-up statement names a specific time, an approximate period, an event, or no time at all.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Lets code schedule reminders from specific commitments and flag vague ones for the rep, without the model resolving any date.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `follow_up_text`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Complete synthetic example

This is fixture `SA05-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "follow_up_text": "I'll follow up on the Monday right after your board meeting wraps, so you'll have the approved numbers in front of you when we talk."
}
```

Expected label: `specific_time_named`.

A weekday (Monday) is named for the follow-up, which the contract defines as a specific time, and it is named together with an event (the board meeting); the tie-break rule selects specific_time_named rather than conditional_on_event, leaving resolution of the actual date to code.

## Code-owned responsibilities

Code resolves a named time to a calendar date, creates the reminder, and records who made the statement; the label never sets a date and never decides whether the statement is a commitment.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a no_time_named or conditional_on_event label prompts the rep to ask for a date.

## Verification recipe

Compare labels with the reminder dates reps set by hand for the same statements; review every no_time_named that a rep scheduled.

This describes required verification work, not checks already performed.

# AP01 — Vehicle system changed by a modification request

[Auto performance catalog]({{ '/auto-performance/' | relative_url }}) · [Evaluation and limitations]({{ '/auto-performance/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/auto-performance.md)

Classify which vehicle system a customer's modification request changes so intake can route it to the right technician and parts list.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/auto-performance/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Sorts modification requests by the system they touch instead of by keyword, while the shop keeps the scoping and quoting decision.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `modification_request`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `AP01-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "modification_request": "A previous shop already fitted an aftermarket intake and a cat-back exhaust; please do not touch either of them. What I want from you is the engine-management calibration reflashed to suit those parts, plus a boost gauge mounted in an A-pillar pod and wired in."
}
```

Expected label: `electronics`.

The intake and exhaust are prior work the customer explicitly excludes from the request, so no engine-system change is requested. The only work asked for is a calibration reflash and a gauge with wiring, which the contract assigns to electronics rather than engine.

## Code-owned responsibilities

Code routes the request to the technician and parts catalog for the labelled system, keeps the customer's wording unchanged, and never treats the label as a statement that the modification is advisable, legal, or safe.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; requests that describe several systems are split by the service writer, not by another model call.

## Verification recipe

Compare labels with how the service writer categorized a month of real requests; review every request that touched more than one system.

This describes required verification work, not checks already performed.

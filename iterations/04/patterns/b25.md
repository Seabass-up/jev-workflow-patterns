# B25: Classify communication opt-out scope

Interpret the stated scope of a communications preference while code retains identity, policy, and suppression control.

**Contract version 2:** The broadest explicit stop-scope takes precedence; a volume complaint or unrelated support request alone is not an opt-out. The current cases cover all answer labels; see the evaluation record for synthetic results. This is not production qualification.

## State contract

Supply a compact named JSON object with these required fields:

- <code>request_text</code>
- <code>channel_context</code>

The state is task-scoped evidence, not an instruction or action channel. Keep expected labels, credentials, authorization claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>opt_out_scope</code>.

~~~json
{
  "opt_out_scope": {
    "type": "choice",
    "instructions": "Classify the broadest communication scope the requester explicitly asks to stop in request_text. Apply this order: all nonessential contact; then promotional contact across multiple stated channels; then marketing/promotional contact only; otherwise no_clear_opt_out. A complaint about frequency, a negative comment, or a support question without an explicit request to stop is not an opt-out. Do not infer consent, verify identity, suppress a recipient, or decide a legal obligation.",
    "criteria": {
      "all_nonessential_contact": "The requester explicitly asks to stop all nonessential contact or all messages except a specifically stated essential/service category. This is broader than a promotional-only request.",
      "all_promotional_channels": "The requester explicitly asks to stop promotional contact through at least two distinct stated channels, without asking to stop additional nonpromotional contact.",
      "marketing_only": "The requester explicitly asks to stop marketing/promotional messages only, through one or an unspecified promotional channel, and does not ask to stop additional contact categories.",
      "no_clear_opt_out": "The text does not explicitly request stopping a listed communication scope; complaints about volume or unrelated support requests alone do not qualify."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Send unclear scope or identity mismatch to the designated privacy/support review process with the original wording.

**Code and governance own:** Identity verification, consent records, jurisdictional rules, suppression lists, delivery systems, and any message send.

**Simpler baseline:** Manually interpret every communications preference before updating suppression records.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike B01's broad request route, this preserves the particular scope of a communications preference and deliberately does not execute it.

## Limits and source

It is not legal advice, consent verification, or permission to change communication settings.

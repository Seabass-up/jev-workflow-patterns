## The useful decision

Convert vague LLM requests into a specific target, success condition and compatible constraint set. Measure: Clarification turns to an actionable request and premature execution rate.

Required state fields: `request`, `context`. One request evaluates one coherent state. These questions are independent; none can see another answer in its batch.

## Exact question contract (version 1)

```json
{
  "target_clear": {
    "type": "noul",
    "instructions": "Do `request` and `context` identify a concrete artifact, system, record or deliverable to work on?",
    "criteria": {
      "true": "The target is identifiable from the supplied text.",
      "false": "The target is an unresolved pronoun, absent or ambiguous."
    }
  },
  "success_clear": {
    "type": "noul",
    "instructions": "Do `request` and `context` state an observable outcome or acceptance condition that distinguishes success?",
    "criteria": {
      "true": "A concrete requested result or check is specified.",
      "false": "Only a vague direction such as better or faster is given."
    }
  },
  "constraint_conflict": {
    "type": "noul",
    "instructions": "Does the requested approach explicitly conflict with a current constraint stated in `context`, without explicitly changing that constraint?",
    "criteria": {
      "true": "A specific current constraint and the requested approach cannot both be satisfied.",
      "false": "No such conflict is established by the supplied text."
    }
  }
}
```

## Consume the JSON and drill down

Read the named answer(s), validate their type and allowed values, then use the documented labels or ordered score as a proposed review signal. Do not treat the result as an executed action.

Follow-up: Code prioritizes a detected constraint conflict, then missing target, then missing success condition. Use fixed clarification templates. A clear request can proceed to normal planning.

Code owns: Own question priority and permission checks in code; retain the user's exact objective and accepted constraints; never interpret probability as approval.

Use provisional Choice/Score confidence ≥ 0.8 and Noul ≤ 0.2 / ≥ 0.8 only as experimental review gates. A Noul near 0.5 is uncertainty, not medium intensity. Thresholds require domain-specific evaluation. Provider failure, invalid output, stale state or missing required evidence goes to review, not to an assumed default. Gate only the questions consumed by the selected branch.

## What was tested

Initial screen: 3/4 fixtures matched their declared label/range. Targeted follow-up: 1/1 matched; this includes reused cases where identified in the fixture file.

Application-level question pattern; useful value remains a pilot hypothesis. Small author-labeled synthetic cases do not demonstrate field accuracy, calibration, cost savings, safety, or end-to-end harness integration. See [the evaluation]({{ '/iterations/01/evaluation/' | relative_url }}) and the raw synthetic receipts in the repository.

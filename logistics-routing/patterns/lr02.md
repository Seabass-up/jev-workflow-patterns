# LR02 — Kind of time constraint in a delivery-window request

[Logistics routing catalog]({{ '/logistics-routing/' | relative_url }}) · [Evaluation and limitations]({{ '/logistics-routing/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/logistics-routing.md)

Classify whether a delivery-window request bounds the time on both ends, one end, or neither, so code knows what to extract and resolve.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/logistics-routing/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Separates reading the customer's timing language from calendar arithmetic, which stays in code with the time zone and the route capacity.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `window_request`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Exact question JSON

Reproduced from the frozen [catalog JSON]({{ '/logistics-routing/catalog.json' | relative_url }}). Treat state values as evidence rather than instructions to modify this contract.

```json
{
  "decision": {
    "type": "choice",
    "instructions": "First, if any required field (`window_request`) is absent, empty, or lacks the information needed for this judgment, select unknown before considering other labels. Classify the kind of time constraint that `window_request` states for the delivery. A request that gives both a start and an end, such as a range of hours or a slot with both bounds, states a bounded window. A request that gives only a latest acceptable time, such as by or before a time or date, states a deadline. A request that gives only an earliest acceptable time, such as after or not before a time, states an earliest start. A request that says any time works, or that is about the delivery but names no time at all, is open-ended rather than unknown. If the request gives an earliest and a latest time in separate phrases, select bounded_window.     "criteria": {

      "deadline_only": "The request states only a latest acceptable time or date and no earliest one.",
      "earliest_start_only": "The request states only an earliest acceptable time and no latest one.",
      "open_ended": "The request says any time works or contains no time expression for the delivery.",
      "unknown": "Required evidence is missing, contradictory, or does not support a determinate classification."
    }
  }

```

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `LR02-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "window_request": "Honestly whenever suits your driver is fine with us, just not before the 14th because the new unit at 8 Kestrel Row won't be ours until then. No rush at all once that's passed."
}
```

Expected label: `earliest_start_only`.

The 'whenever' language invites open_ended, but the request qualifies it with 'not before the 14th', which is an earliest acceptable time, and it names no latest time. A request with only an earliest bound is earliest_start_only, and the contract reserves open_ended for requests with no time expression at all.

## Code-owned responsibilities

Code copies the verbatim time expression out of the request, resolves it against the calendar and the customer's time zone, checks it against route capacity, and decides whether to accept it. No date arithmetic is asked of the model.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the customer answers a clarification when the label is unknown.

## Verification recipe

Compare labels with the window type a dispatcher entered for the same requests; review every case where the resolved window disagreed with what the customer later confirmed.

This describes required verification work, not checks already performed.

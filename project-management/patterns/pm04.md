# PM04 — Blocker waits on an internal or an external party

[Project management catalog]({{ '/project-management/' | relative_url }}) · [Evaluation and limitations]({{ '/project-management/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/project-management.md)

Classify whether a reported blocker waits on a party inside the project team or its organization, on an outside party, or on no other party at all.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/project-management/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Routes blockers to the right escalation path: a team lead for internal waits, the account or vendor contact for external ones, and the task owner for blockers that need no one else.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `blocker_report`
- `party_list`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `PM04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "blocker_report": "The data-load task for the Kestrel analytics pilot is blocked. Brightwater Logistics.example, the customer, sent the anonymized sample dataset last Tuesday, so nothing further is needed from them. The load cannot start until the Halcyon Security Review Board signs off on storing that dataset in the shared staging bucket; the request has sat in their queue since Thursday. Our own pipeline is built and its tests pass.",
  "party_list": [
    {
      "party": "Kestrel project team",
      "side": "internal"
    },
    {
      "party": "Halcyon Security Review Board",
      "side": "internal (project organization)"
    },
    {
      "party": "Brightwater Logistics.example",
      "side": "external (customer)"
    },
    {
      "party": "Orrin Cloud Services.example",
      "side": "external (vendor)"
    }
  ]
}
```

Expected label: `internal_dependency`.

The only party the work is stated to wait on is the Security Review Board, which party_list marks internal; the external customer is named but has already delivered, so there is no external wait and the both-parties rule does not apply. The report also describes no problem within the work itself, so no_other_party does not fit.

## Code-owned responsibilities

Code owns the escalation path for each label, the party list and its revision, and any aging or due-date calculation; it never contacts an external party on a label alone.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the party list is updated when the report names a party the list omits.

## Verification recipe

Compare labels with how the project manager escalated a month of blockers; review each no_other_party label that was later escalated to another party.

This describes required verification work, not checks already performed.

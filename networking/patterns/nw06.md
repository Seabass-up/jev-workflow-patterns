# NW06 — Runbook step states its own reversal

[Networking catalog]({{ '/networking/' | relative_url }}) · [Evaluation and limitations]({{ '/networking/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/networking.md)

Classify whether one runbook step says how its effect would be reversed, as written.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/networking/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Flags state-changing steps with no stated reversal during runbook review, before a change window, without deciding whether the step is safe.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `runbook_step`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `NW06-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "runbook_step": "Step 4: Confirm that the pre-change backup dist-sw-02-prechange.cfg is present on flash and matches the running configuration, and record its checksum in the change ticket. Wait for the change lead's go-ahead in the bridge channel before continuing to step 5."
}
```

Expected label: `no_state_change`.

The step only verifies, records, and waits, which the contract says changes no device, service, or record state. Naming a saved configuration inside a verification step does not make the step a state change with a stated undo, so undo_stated does not apply.

## Code-owned responsibilities

Code verifies that any named backup or saved configuration exists, records approvals, and executes nothing; people decide whether a step may run.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a step labeled undo_not_stated goes to the runbook owner.

## Verification recipe

Compare labels with a reviewer's reversibility annotations on existing runbooks; review every undo_stated whose named reversal a reviewer found missing.

This describes required verification work, not checks already performed.

# SA03 — Which buying signal the prospect states

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Identify whether a prospect message states a budget, a timeline, or a decision process so qualification fields can be filled from the prospect's own words.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Fills qualification fields from what the prospect actually wrote and flags messages that state nothing, while code keeps amounts and dates.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `prospect_message`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `SA03-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "prospect_message": "To be upfront, we haven't set aside any money for this yet and there's no hard date on our side. What I can tell you is how it would work: any new tool goes through our security review first, then Marta in procurement handles the contract, and our VP of Operations makes the final call after a side-by-side of the shortlisted vendors."
}
```

Expected label: `decision_process_stated`.

The message describes who decides, the review and procurement steps, and how shortlisted vendors will be compared, which is a decision-process signal; saying no money is set aside and no date exists states neither an amount nor a date, so there is no second signal and multiple_signals_stated does not apply.

## Code-owned responsibilities

Code extracts and stores the amount, date, and named roles exactly, compares them with qualification thresholds, and sets the pipeline stage; the label only says which kind of signal the text states.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One follow-up call on the reply when the label is no_signal_stated and the rep has asked a qualifying question.

## Verification recipe

Compare labels with qualification fields the sales team filled for the same messages; measure missed signals first, then false signals.

This describes required verification work, not checks already performed.

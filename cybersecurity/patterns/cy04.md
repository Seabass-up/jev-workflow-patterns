# CY04 — Incident report states the conditions a severity definition requires

[Cybersecurity catalog]({{ '/cybersecurity/' | relative_url }}) · [Evaluation and limitations]({{ '/cybersecurity/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/cybersecurity.md)

Classify whether an incident report states, as established, the conditions that a supplied severity definition requires for that level.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/cybersecurity/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Applies the organization's own severity wording to a report consistently, while the incident lead assigns the severity and code compares any numeric thresholds.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `incident_report`
- `severity_definition`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `CY04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "incident_report": "At 14:05 the customer order portal (orders.example) became unavailable to all customers and remained down until 15:20; the outage is confirmed and was caused by a failed certificate renewal on the load balancer. Whether any customer records were exposed during the failover is still under investigation, and there is no indication of external access to any production system.",
  "severity_definition": "Severity 2 applies when any one of the following is established: (a) an external party has gained access to a production system; (b) customer personal data has been exposed outside the organization; (c) a production service used by customers is unavailable."
}
```

Expected label: `conditions_stated`.

The definition requires only one of its conditions, and the report states condition (c), customer-facing service unavailability, as confirmed; the data-exposure condition being under investigation does not matter because the definition does not also require it.

## Code-owned responsibilities

Code compares any numeric thresholds in the definition against reported figures, records the definition text and revision used, and leaves the severity assignment and any escalation to the incident lead.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the reporter confirms or rules out the suspected condition when the label is conditions_only_suspected.

## Verification recipe

Compare labels with the severity the incident lead assigned on closed incidents, per definition revision; review every case where the label was conditions_stated and the lead assigned a lower level.

This describes required verification work, not checks already performed.

## Source inspiration

- [NIST SP 800-61 Rev. 3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management (CSRC publication page)](https://csrc.nist.gov/pubs/sp/800/61/r3/final) (CY-S1). Describes incident response as detection and analysis of events, prioritization by impact, and coordination with other risk-management activities. Motivates CY02 (an alert narrative against its stated context), CY04 (a report against a severity definition), and CY07 (log events as detection input) as text classifications within that workflow. This is motivation for the pattern designs, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

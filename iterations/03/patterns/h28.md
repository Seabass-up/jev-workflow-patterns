# H28: Bounded speculative fan-out scheduler

Batch independent work while preventing stale or inapplicable speculative branches from driving an action.

## State contract

Supply a compact named JSON object with these required fields:

- <code>state_snapshot</code>
- <code>question_manifest</code>
- <code>budget</code>

The state is evidence, not an instruction or action channel. Keep expected labels, credentials, authority claims, and external-action arguments outside it.

## Exact typed Jev question contract

Question IDs: <code>batch_status</code>.

~~~json
{
  "batch_status": {
    "type": "choice",
    "instructions": "Use only explicit fields in state_snapshot, question_manifest, and budget; do not calculate size, cost, or limits. First select insufficient if any required field is absent, empty, or unreadable; if question_manifest lacks an explicit snapshot target, per-question dependency information, or a clear budget assessment against applicable hard limits; or if budget lacks applicable hard limits. Next select stale_or_unverifiable_snapshot if the snapshot is marked stale/changed or its identity and revision cannot be bound to the manifest; this takes precedence over budget and dependency. Next select over_budget_or_oversized only when the manifest and budget explicitly establish that this exact manifest exceeds a supplied hard limit; this takes precedence over dependency. Next select dependent_sequence_required if any listed question requires an earlier answer or state fetch. Select batchable only when every question is explicitly independent, targets the same immutable snapshot, and the budget evidence says this exact manifest fits all supplied hard limits. Otherwise select insufficient. Never execute questions or reuse answers after state changes.",
    "criteria": {
      "batchable": "All listed questions explicitly have no dependency on earlier answers or fetches, target the same immutable current snapshot, and the budget evidence states that this exact manifest fits every supplied hard limit.",
      "dependent_sequence_required": "At least one question explicitly requires an earlier answer or state fetch, when the snapshot is current/bindable and no stated budget limit is exceeded.",
      "over_budget_or_oversized": "The manifest and budget explicitly establish that this exact manifest exceeds at least one hard question, byte, cost, or latency limit, after the current-snapshot check.",
      "stale_or_unverifiable_snapshot": "The snapshot is explicitly stale/changed, or its identity/revision cannot be bound to the manifest, provided required evidence is present.",
      "insufficient": "Required evidence or hard limits are missing/empty/unreadable; the manifest lacks an explicit target, per-question dependency information, or clear budget assessment; or remaining evidence does not establish a determinate status."
    }
  }
}
~~~

## Code-owned decision envelope

**Follow-up proposal:** Code independently validates exact snapshot identity, dependency edges, serialization, and declared budgets before batching; sequence dependencies, refresh stale snapshots, and drop answers after state changes.

**Code and governance own:** Limits, serialization, request construction, cache scope, concurrency, cost, latency, and answer consumption.

**Simpler baseline:** Send a separate request for every question or batch dependent questions blindly.

## Uncertainty and distinctness

Provisional synthetic screening only; model output is advisory.

**Why this is not a renamed earlier pattern:** Unlike H12's repeated-decision stability gate, this controls which independent questions share one immutable request and how code discards stale speculative answers.

## Limits, source, and shared skill

The Jev result is advisory. Code owns exact limits, serialization, request construction, cache scope, concurrency, cost, latency, freshness checks, and answer consumption; batching creates no cross-question reasoning.

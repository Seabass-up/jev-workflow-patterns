# SA08 — What a competitor mention does in the message

[Sales catalog]({{ '/sales/' | relative_url }}) · [Evaluation and limitations]({{ '/sales/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/sales.md)

Classify whether a prospect's mention of a named competitor asks for a comparison, states the competitor as the incumbent, names it as an alternative under evaluation, or is a passing mention.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/sales/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Routes comparison questions to the right material and incumbent situations to the right play without a rep re-reading every mention.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `prospect_message`
- `competitor_name`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `SA08-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "prospect_message": "Some context: we're on Brightline today and have been for about three years, with the contract running through next spring. What I'd really like from you is a straight comparison of your reporting against Northwind's, since Northwind is the other vendor that made our shortlist.",
  "competitor_name": "Brightline"
}
```

Expected label: `incumbent_stated`.

The comparison the prospect asks for concerns Northwind, not the matched name, so comparison_requested does not describe what the Brightline mention does; for Brightline the message states current use under a contract, which is an incumbent statement.

## Code-owned responsibilities

Code matches competitor names exactly against the maintained list, records which name was matched, attaches the approved comparison material, and leaves every claim about a competitor to reviewed content and the account owner.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; when several competitor names are matched, code runs one call per name.

## Verification recipe

Compare labels with how reps tagged competitor mentions on a quarter of opportunities; review every incumbent_stated that a rep tagged as a comparison request.

This describes required verification work, not checks already performed.

# FN07 — Approver reply: explicit approval, conditional approval, deferral, or rejection

[Finance catalog]({{ '/finance/' | relative_url }}) · [Evaluation and limitations]({{ '/finance/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/finance.md)

Classify what an approver's reply does with a specific request so the request record can be updated and conditions tracked.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/finance/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Stops a hedged or postponed reply from being treated as approval, while the approval itself is recorded only by the approval system and the approver.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `approval_request`
- `approver_message`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Exact question JSON

```json
{
  "decision": {
    "type": "choice",

Classify what `approver_message` does with it. Approval as asked with no restriction is explicit approval. Approval that depends on a stated condition, a change, a reduced amount or scope, or another person's sign-off is conditional approval. A remark that does not restrict this approval, such as advice for future requests, does not make it conditional.       "conditional_approval": "The message approves only subject to a stated condition, change, reduction, or another person's sign-off on this request.",
      "deferral": "The message postpones the decision, asks for more information, or refers the request to someone else without approving or declining.",
      "rejection": "The message declines the request as asked.",

    }
```

## Policy recorded with its option count

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `FN07-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "approval_request": "Request AR-EX-7 from Dana Okafor (Field Services): approve purchase of twelve ruggedised tablets, one per field crew, from Kestrel Devices (sales@kestreldevices.example), with a two-year protection plan on each.",
  "approver_message": "Dana, I'm not approving AR-EX-7 as submitted. Twelve units for every crew is more than I can justify this quarter, and I don't think the protection plan earns its cost. If you want to pilot this, write up a new request for the three Dispatch crews only, without the plan, and I'll consider that one on its own merits. Thanks for the detailed quote though."
}
```

Expected label: `rejection`.

The message declines the request as asked ('not approving ... as submitted') and only invites a fresh, narrower submission; the contract says a decline is a rejection even when it invites resubmission, so it is neither a conditional approval of a reduced scope nor a deferral.

## Code-owned responsibilities

Code checks the approver's authority and limit against the request, records an approval only through the approval system with the message as evidence, and tracks conditions to closure; the label never creates an approval.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check when a later message from the same approver arrives on the same request.

## Verification recipe

Compare labels with approvals recorded in the approval system for a quarter; review every message the label called explicit_approval that a person recorded differently.

This describes required verification work, not checks already performed.

# HR06 — Offer letter states every required element

[Human resources catalog]({{ '/human-resources/' | relative_url }}) · [Evaluation and limitations]({{ '/human-resources/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/human-resources.md)

Check whether an offer letter states each element the organization's checklist requires, such as title, start date, compensation, and contingencies.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/human-resources/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

<div class="callout warning"><p><strong>Provisional.</strong> At least one screening case disagreed with its authored label or did not complete. The disagreement is preserved on the evaluation page; neither the contract nor the label was changed after inference.</p></div>

## Proposed benefit

Catches a merged template that dropped or doubled an element before the letter is sent; the values themselves and the approval stay with people and code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `offer_letter_text`
- `required_elements`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

```json
    "criteria": {

    }
  }

```

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `HR06-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "offer_letter_text": "Dear Tomas, Northwind Freight (northwindfreight.example) is pleased to offer you the position of Dispatch Coordinator, reporting to Lena, Operations Manager. Your start date will be the date you agreed with Marta on your call last Thursday. Your base salary will be $58,000 per year, paid biweekly. This offer is contingent on a satisfactory background check and completion of reference checks. Compensation summary for your records: base salary $56,000 per year; benefits begin the first of the month after your start.",
  "required_elements": [
    "job title",
    "start date",
    "base salary",
    "reporting manager",
    "contingencies"
  ]
}
```

Expected label: `inconsistent_elements`.

The start date is only referenced as agreed on a call, which the contract says does not count as stated, so an element is missing; base salary is also given two different values ($58,000 and $56,000), and the contract's tie-break says that when elements are both missing and inconsistent, inconsistent_elements is selected.

## Code-owned responsibilities

Code holds the checklist per letter template and jurisdiction, compares the stated values with the approved offer record exactly, and controls who may send the letter. The label never approves an offer.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the recruiter revises the letter.

## Verification recipe

Run past letters with known omissions through the check; measure missed omissions per template before measuring anything else.

This describes required verification work, not checks already performed.

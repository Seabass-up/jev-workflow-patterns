# NW08 — Alert requires a response under the supplied policy

[Networking catalog]({{ '/networking/' | relative_url }}) · [Evaluation and limitations]({{ '/networking/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/networking.md)

Classify whether a monitoring alert requires a response, is informational only, or is not addressed, according to a supplied policy text.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/networking/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Applies the team's own written alert policy consistently across alert wording from different monitors, while paging and thresholds stay in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `alert_text`
- `alert_policy`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

```json
    "criteria": {

      "informational_only": "The policy says an alert of this kind, in the condition the alert text describes, is recorded only, resolves on its own, or needs no action.",
      "policy_does_not_address": "The policy has no clause that covers the kind of alert the text describes.",
      "unknown": "Required evidence is missing, contradictory, or does not support a determinate classification."
    }
  }
}
```

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `NW08-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "alert_text": "LINK FLAP: lab access switch, port 12, 4 transitions in 60 seconds. Environment: lab. Device: lab-sw-03.example.",
  "alert_policy": "1. Any alert reporting an interface or link going down or flapping requires acknowledgement by the on-call engineer within 15 minutes. 2. Link flap alerts from lab access switches, regardless of transition count, are recorded only and clear on their own; no action is taken. 3. Alerts about power supply or fan failures on any device require a response."
}
```

Expected label: `informational_only`.

Clauses 1 and 2 both cover a link flap alert, and the contract says the clause that names the alert's kind more specifically wins; clause 2 names link flaps on lab access switches and is the more specific. Clause 2 also states that the transition count is irrelevant, so no unresolved threshold comparison forces unknown.

## Code-owned responsibilities

Code owns paging, escalation, de-duplication, maintenance suppression, and every threshold comparison; the label classifies the alert under the supplied policy text only.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; an alert the policy does not address goes to the on-call engineer with the policy gap noted.

## Verification recipe

Replay a month of alerts against the on-call engineer's acted or ignored record; measure requires_response alerts that were ignored and informational_only alerts that were acted on.

This describes required verification work, not checks already performed.

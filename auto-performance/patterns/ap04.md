# AP04 — Symptom category described by a tuning note and its flagged readings

[Auto performance catalog]({{ '/auto-performance/' | relative_url }}) · [Evaluation and limitations]({{ '/auto-performance/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/auto-performance.md)

Classify the symptom category a tuner's note and code-flagged readings describe so the tuning log can be tagged consistently.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/auto-performance/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Tags pulls by the symptom described, using comparisons code has already made, so the tuner can review knock and lean events first; the tuner keeps the diagnosis and every change to the calibration.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `tuning_note`
- `reading_flags`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

Review when confidence is below 0.8. With 6 options, that floor is equivalent to a top probability of 0.8333; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `AP04-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "tuning_note": "Third pull of the afternoon. Knock sensor stayed quiet for the whole run and no timing was pulled, so ignition is not what I am chasing. Near the top of third gear the car stumbled and the log shows a cut; pulled the plugs afterward and they were black and wet with fuel.",
  "reading_flags": [
    "knock retard: none recorded, within target",
    "lambda: below target from mid-range through redline",
    "coolant temperature: within target",
    "misfire count: above zero on cylinder three during the cut",
    "intake air temperature: within target"
  ]
}
```

Expected label: `misfire`.

Knock is mentioned only to be negated, so it does not apply. The note and flags describe both a misfire (stumble, cut, misfire count) and a rich condition (lambda below target, fuel-fouled plugs), and the stated precedence puts misfire ahead of rich.

## Code-owned responsibilities

Code compares every logged reading with the tuner's stated targets and writes the flags in words, asks this question only when the tuner marks an issue or any flag is raised, and never changes a calibration from a label.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; a note that describes several symptoms is tagged by the stated precedence and the tuner adds the rest.

## Verification recipe

Compare labels with the tags the tuner applied when reviewing the same logs; measure missed knock descriptions first.

This describes required verification work, not checks already performed.

## Source inspiration

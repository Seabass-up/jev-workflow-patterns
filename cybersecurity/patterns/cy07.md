# CY07 — Authentication outcome described by a log event

[Cybersecurity catalog]({{ '/cybersecurity/' | relative_url }}) · [Evaluation and limitations]({{ '/cybersecurity/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/cybersecurity.md)

Classify whether one log event describes a successful authentication, a failed one, an account lockout, or no authentication outcome.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/cybersecurity/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Normalizes the wording of many systems' authentication messages into one outcome label, while counting, thresholds, and account actions stay in code.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `log_excerpt`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

```json
{
  "decision": {
    "type": "choice",
    "instructions": "First, if any required field (`log_excerpt`) is absent, empty, or lacks the information needed for this judgment, select unknown before considering other labels. `log_excerpt` is the text of one log event as the system wrote it, supplied by code one event at a time. Classify the authentication outcome the event describes. An accepted sign-in, a granted session, or a credential verified as valid is a success. A rejected sign-in, an invalid or wrong credential, or a denied authentication is a failure. An event that is not an authentication attempt, such as a session timeout, a file read, or a configuration change, or an attempt whose result is not stated, is no authentication outcome. ## Policy recorded with its option count
```

Review when confidence is below 0.8. With 5 options, that floor is equivalent to a top probability of 0.84; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `CY07-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "log_excerpt": "2026-09-22T08:14:03Z portal-auth.example AUTH: password rejected for user m.castellano (reason: credential mismatch) from 198.51.100.23; failed-attempt counter 2 of 5, lockout threshold not reached, account remains enabled."
}
```

Expected label: `authentication_failure`.

The event records a rejected credential, and it mentions the lockout threshold only to state that it was not reached and the account remains enabled, so no lockout is described and the failure-plus-lockout rule does not apply; counting toward the threshold is code's job.

## Code-owned responsibilities

Code parses timestamps, account and host identifiers, and source addresses, counts events, applies lockout and alerting thresholds, and takes any account action. The label only names the outcome one event describes.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

None; unknown events go to the parser backlog, not to another model call.

## Verification recipe

Run a labeled sample of authentication events from each log source through the check; measure, per source, the failures and lockouts labeled as no authentication outcome first.

This describes required verification work, not checks already performed.

## Source inspiration

- [NIST SP 800-92, Guide to Computer Security Log Management (CSRC publication page)](https://csrc.nist.gov/pubs/sp/800/92/final) (CY-S5). Describes log management, including authentication events recorded by many systems in differing formats and the analysis that depends on normalizing them. Motivates CY07 as a normalization of one event's stated authentication outcome, with parsing, counting, and thresholds in code. Motivation, not evidence of Jev performance.
- [NIST SP 800-61 Rev. 3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management (CSRC publication page)](https://csrc.nist.gov/pubs/sp/800/61/r3/final) (CY-S1). Describes incident response as detection and analysis of events, prioritization by impact, and coordination with other risk-management activities. Motivates CY02 (an alert narrative against its stated context), CY04 (a report against a severity definition), and CY07 (log events as detection input) as text classifications within that workflow. This is motivation for the pattern designs, not evidence of Jev performance.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.

# CY06 — Policy-exception request names a compensating control

[Cybersecurity catalog]({{ '/cybersecurity/' | relative_url }}) · [Evaluation and limitations]({{ '/cybersecurity/evaluation/' | relative_url }}) · [Kernel reference module](https://raw.githubusercontent.com/Seabass-up/jev-workflow-patterns/main/skills/jev-question-kernel-catalog/references/cybersecurity.md)

Classify whether a request to be excused from a security requirement names a measure that addresses the same exposure the requirement exists to limit.

This is a proposed, bounded text judgment. Consult the [evaluation record]({{ '/cybersecurity/evaluation/' | relative_url }}) for observed results; the fixture labels below are intended outputs.

## Proposed benefit

Separates requests that come with a compensating control from those that ask to drop a requirement outright, before the risk owner reviews them.

This is a proposed benefit, not an observed outcome. All fixtures on this page are synthetic.

## Required named state

Supply the following named fields as the evidence packet:

- `exception_request`
- `policy_requirement`

Code deterministically returns `unknown` without invoking Jev when any required named field is absent or empty; the model is not the required-field gate. The live missing-input case below probes the contract wording, not that gate.

## Policy recorded with its option count

Review when confidence is below 0.8. With 4 options, that floor is equivalent to a top probability of 0.85; a threshold is not portable to a contract with a different option count. These values are provisional workflow policy, not calibration.

## Complete synthetic example

This is fixture `CY06-4`, from the **challenge** split. Its author received the question contract without the design fixtures or model results; the expected label is an authored interpretation of the contract, not a Jev prediction.

```json
{
  "exception_request": "We ask to be excused from encrypting the backups of the orders database for six months because encrypted backups break our current restore tooling. In place of encryption we will run a nightly integrity check on every backup file, retain backups for 90 days, and we accept the residual risk; we will comply once the tooling vendor ships encryption support next quarter.",
  "policy_requirement": "Production database backups must be encrypted at rest. Purpose: to limit disclosure of customer data if backup media or backup storage is accessed by an unauthorized party."
}
```

Expected label: `unrelated_measure_named`.

The request names specific measures, nightly integrity checks and 90-day retention, so it is not no_control_named, but those measures address corruption and availability rather than the disclosure exposure the requirement's stated purpose names, and the remaining content is risk acceptance and a promise to comply later, which the contract also classes as unrelated.

## Code-owned responsibilities

Code records the requirement text and revision, the exception's expiry, and the risk owner's decision. A compensating_control_named label does not grant the exception, and the adequacy of the control is the risk owner's judgment.

The judgment is advisory. Code and the responsible person retain control of exact identifiers, data access, state changes, and consequential verification.

## Bounded follow-up

One re-check after the requester adds a control description when the label is no_control_named.

## Verification recipe

Compare labels with risk-owner decisions on closed exception requests; review every request approved with a control the label called unrelated or absent.

This describes required verification work, not checks already performed.

## Source inspiration

- [NIST SP 800-53 Rev. 5, Security and Privacy Controls for Information Systems and Organizations (CSRC publication page)](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) (CY-S3). Catalog of security and privacy controls that includes least-privilege access, the use of compensating controls where a control cannot be implemented as written, and supply chain risk management including supplier assessments. Motivates CY05 (task-bound access justification), CY06 (compensating control named in an exception request), and CY08 (vendor questionnaire answers). Motivation only, not evidence of Jev performance; no control is applied by the model.

These sources motivate the design problem and its boundaries. They do not demonstrate Jev performance on this question.
